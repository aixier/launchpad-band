### 0.1 设备事实核对(设计受这些约束)

| # | 事实 | 出处 | 对音乐玩法的含义 |
|---|---|---|---|
| 1 | 80 个键:8x8 主盘 + 8 个顶排圆键(CC 104~111)+ 8 个侧列圆键(发 note) | [MK2手册·Basic Communication / Layouts] | 主盘当"乐器",16 个圆键当"控制"。**按编号称呼,不按屏幕位置**(照片竖拍,易认错) |
| 2 | **按键没有力度**:按下发最大力度 note-on,松开发力度 0 | [MK2手册·Basic Communication] | 做不了轻重表现;**力度要由软件根据节拍/音位"人工赋予"**,否则声音像机器。这被设计成特性,见 4.4 |
| 3 | 灯:调色板 0~127 号;或 SysEx RGB,每色 0~63,一条消息最多 80 灯 | [MK2手册·Colours / RGB Mode] | 能做"音名配色"。是否真是 RGB 灯 `[待验证]`(README 已标) |
| 4 | 闪烁/呼吸用调色板号(非 RGB),节奏可由 MIDI 时钟(F8,24/拍,40~240 BPM)驱动 | [MK2手册·Flashing/Pulsing/MIDI Clock] | **"下一个该按的键"可以用硬件自带的呼吸灯表达,不占 USB 带宽,且能和节拍同步** |
| 5 | 灯只写不读(手册无读回) | [MK2手册] | 软件必须自己存一份灯色表 |
| 6 | 滚动文字只有 ASCII | [MK2手册·Text scrolling] | **中文一律走电脑屏幕**,灯盘不负责说话 |
| 7 | 设备无声音输出 | 用户描述 | 声音完全由电脑出,"按键→出声"延迟由电脑音频链决定,是本方案最大的体验风险 |
| 8 | 主盘键位:note = 11 + 列 + 10×行(行从下往上,0 起) | [MK2手册·Layouts],"加 1 右移、加 10 上移" | 适合软件当"格子"用。侧列 note 编号(推测 19、29…89)和 Mini 是否同表 `[待验证]` |
| 9 | 有几颗键帽缺角 | [README]、`photos/top-view.jpg` | 上机第一件事:逐键测按压是否灵敏、有无误触 |
| 10 | **文档错配风险**:`docs/launchpad-mini-user-guide-v2-en.pdf` 的内容是带 USB-C 口、有 Live/Programmer/Legacy 三模式的型号(我读到的原文:"USB-C Socket"、"Programmer Mode"),**不像是本机 MK2 的手册**(很可能是后一代 Mini)。README 把它当成本机手册 | 该 PDF 第 7 项接口说明、"Legacy, Live, and Programmer Modes" 章 | **不得用它判断本机行为**(尤其"有无力度感应"、模式切换键)。本机以 MK2 手册 + 上机实测为准。`[待验证]`,建议修正 README |

> 一个事实决定了方案取向:**灯盘本身不发声、没有力度、没有屏幕,但"一个会发光的 8x8 格子 + 64 个确定的按键位置"很适合当"不会错的乐器面板"。** 强项是"格子和灯",短板是"声音和文字"——短板交给电脑,强项做到极致。

## 1. 核心洞察

### 1.1 小白为什么觉得音乐"难/无聊"(假设,非调研结论;验证方法见第 6 节)

下面五条是我基于常识的假设。每条后面写了"这个产品怎么回应"。

| # | 假设 | 一句话 | 本产品的回应 |
|---|---|---|---|
| H1 | **一开口就怕出错**:钢琴 12 个音里有 5 个"黑键",按错立刻刺耳,小白第一次接触的反馈是惩罚 | "我按错了,好丢人" | 键盘上**不存在会撞耳的音**(1.2) |
| H2 | **一个人的旋律不好听,好听来自"乐队感"**:节奏 + 低音 + 和声 + 旋律叠在一起。小白只能做一层,所以永远听着像"练习" | "我弹的不像歌" | **AI 乐队补齐其余三层**,你只负责最好玩的那层 |
| H3 | **门槛被包装成术语和符号**:调、和弦、五线谱、DAW。这些其实是"怎么记录和沟通",不是"怎么享受" | "我不懂乐理" | **全程零术语**;概念只以"颜色/亮度/一个按钮的效果"出现 |
| H4 | **反馈周期太长**:练几个月才有成果 | "没意思" | **第一次按键就进入"在演奏"状态**,目标 10 秒内 |
| H5 | **只会听,不知道自己能"参与"**:把音乐当成别人做好的成品 | "音乐是别人的事" | **你的每个动作都会改变整支乐队的表现**,让人体会"我在影响音乐" |

诚实提醒:H1~H5 里,H1 和 H2 有较强的常识支撑,H3~H5 更像产品信念。**最大的不确定性是"小白在 5 分钟后还想不想继续"**,不是"第一次好不好玩",见 6.2 的次日回访。

### 1.2 为什么"8x8 网格 + 音阶约束"能变成"不会错的游戏"

**核心做法:把网格上的每个键都映射成"和当下乐队合得来的音",让小白没有机会按到不和谐的音。** 三层保险:

1. **音高层 —— 只给五声音阶。**
   - 五声音阶(pentatonic)是每八度只有 5 个音(例:C D E G A)的音阶,里面**没有半音关系**,所以任意乱按不会出现最刺耳的小二度碰撞。依据:乐理常识,Wikipedia "Pentatonic scale"、"Minor second" `[待验证]`。
   - 教育界早有现成做法:**奥尔夫乐器(Orff Schulwerk)的音条可以拆掉**,让孩子用五声音阶即兴不会出错 `[待验证,来源 Wikipedia "Orff Schulwerk"]`。
   - 中国传统的五声调式(宫商角徵羽)与此同构,可以做"国风"主题卡 `[待验证]`。
   - 流行文化里的例子:Bobby McFerrin 2009 年 World Science Festival 演示"观众会本能地唱五声音阶" `[待验证]`。
2. **和声层 —— AI 乐队只用"和五声音阶兼容"的和弦进行。**
   - 五声音阶的 5 个音在 I、vi、IV、V 这几个和弦上都能站得住(最多只是"挂留/9 度/6 度"这种柔和的色彩),这是流行歌的"四和弦"常用走向:I–V–vi–IV `[待验证,Wikipedia "I–V–vi–IV progression"]`。
   - **这条要工程化而不是相信**:每张乐队卡(见 4.3)入库前,用脚本对"网格上的所有音高"×"该卡的每个和弦"检查,**不允许出现和弦音的小二度/小九度冲突**;不合格的卡不上线。这是可自动测的。
3. **时间层 —— 乐队永远稳定地打着拍子。**
   - 小白的节奏感不稳,但**鼓和贝斯稳**时,听众会把"稳"归功于整体。不对玩家的音做延后量化(延后会让按键"不跟手"),只对**录下来回放的内容**做量化(P1)。

**为什么我认为这成立(以及哪里可能不成立)**
- 成立的部分:有同类产品验证过"受限音高 + 自动伴奏"能让新手快速得到好听的结果——Incredibox(拖拽音轨,自动同步、几乎不会难听)`[待验证]`;Google Magenta 的 Piano Genie(8 个按钮驱动钢琴演奏)`[待验证,Donahue et al. 2018]`;Chrome Music Lab Song Maker(可选五声音阶)`[待验证]`。
- **不成立的风险**:五声音阶对**西方流行/国风**友好,对想弹"别的风格"的人未必;**"好听但很平"**——限制太多,几分钟后可能无聊。所以必须有"渐进解锁"(见 4.8),让人感觉自己在进步,而不是永远被围起来。
- **另一个风险是"代劳感":** 如果好听主要来自乐队,玩家可能觉得"这不是我弹的"。设计上要保证**玩家的音是主角、乐队是在回应你**;验收里专门问"这是你弹的还是电脑弹的"(6.2)。

### 1.3 一句话产品定位

> **「你按键,一支会听你、跟着你变的 AI 乐队就进来了。」**
> 不是教你音乐,是让你在 10 秒内站在舞台中间;玩着玩着,不知不觉知道了"为什么这样好听"。

对"专业用法平面化"的回答:
- 专业用法(Ableton Session View 触发 clip、鼓垫)的前提是:装 DAW、做 clip、会选调、会对齐速度。[用户手册讲的是 Ableton Live 触发 clip 的流程,见 `docs/launchpad-mini-user-guide-v2-en.pdf`——注意它的型号错配,仅作"专业用法长什么样"的旁证。]
- 我们把这些**全部预先替用户做掉**:调、速度、和弦进行、鼓型都由"乐队卡"决定,键盘上只剩"按"。**把音乐里最难的部分(选择和对齐)变成 AI 的工作,把最好玩的部分(即兴、改变情绪)留给人。**

### 1.4 设计主线:玩中学 + 创作感 + 灯光(用户补充)

**一句话:没有"学习环节",只有"发现时刻"。** 每个乐理概念都对应一个**操作 + 一个灯光/声音后果**,玩家做了就会感到"咦,变了",我们不解释。

| 概念(玩家不会看到这个词) | 藏在哪个玩法里 | 玩家的"发现" |
|---|---|---|
| 节拍 | 盘面随拍脉动;乐队一直稳稳地走 | "踩着灯按就很顺" |
| 音高高低 | 越往外、越亮的键越高 | "往那边是尖的" |
| 主音/"回家" | 主音键最亮;乐句停在它上面最"落地" | "停在亮键上像说完话了" |
| 稳定与紧张 | 和弦音亮、其他音暗 | "按亮的更稳" |
| **和弦进行** | **编曲视图:按下的格子组合 = 每小节的和弦,灯盘变成一排色块** | "这几块这样排像一首歌" |
| **乐句/循环** | **"留住这一段":你刚弹的那几小节自动变成循环,盘面上自己重复亮起** | "我弹的会自己重复" |
| **分层/编曲** | **每留住一段,就多一个乐器**;盘面上多一种颜色的"幽灵手指" | "加一层就丰满了" |
| 大调/小调(情绪) | 换风格卡:同样的按法,情绪变了 | "同样的键,换了心情" |
| 留白/力度 | 能量档:乐队放轻时,你的音更突出 | "安静一点反而好听" |

**创作感的底线:** 每次操作的结果都被保存进"这首歌"(内部工程模型,第 9 节),最后能存、能放、能发。**不是"跟着弹",而是"你一层层搭出来了一首"。**

## 2. 用户画像与"第一次拿到的 10 分钟"

**以下三类是假设画像,不是调研结论。** 共同前提:拿到的是一块会亮的格子,不知道它是干嘛的,没有说明书耐心;电脑已由我们(原型阶段)装好并连好。

### 画像 A:孩子(假设 7~10 岁),家长在旁

- **想要:** 一按就有反应、好玩、能"炫"。家长想要"不是纯刷屏"。
- **不想要:** 读字、被纠正、等待。
- **为什么会想玩:** 一按,鼓和贝斯"哗"地进来——像"我变成了指挥/乐手"。
- **为什么会想再玩:** 8 个心情颜色键能瞬间换整支乐队(像换服装);想让乐队"更燃"(高潮键);想把自己的歌留下来给别人听。

| 时间 | 发生什么(灯盘 / 声音 / 屏幕) | 关键点与风险 |
|---|---|---|
| 0:00 | 插上,灯盘从中间向四周亮起暖色波纹,逐步显现"一片彩色的格子"。屏幕大字:**"按一下发光的键"** | 灯不亮=立刻失败。必须开机自检 |
| 0:05 | 孩子戳了一个键:**响起一个干净的钢琴音,键瞬间亮白再退回自己的颜色** | 首次出声目标 ≤10 秒(拟定) |
| 0:08 | 再戳两三下后,**鼓+贝斯+和弦"进"了**,屏幕:"乐队来了!" | 这是魔法时刻。进场时机定在下一小节线,不要突兀 |
| 0:30 | 孩子在盘面上乱按,**每个音都好听**,有一两个键在"呼吸"(带路灯) | 乱按也 OK 是设计目标 |
| 1:30 | 孩子发现侧列的颜色键:按一下,整支乐队变成"海盗风/梦幻风" | 这是"更多可玩"的发现点,需要灯光暗示 |
| 4:00 | 孩子按"高潮"键,鼓猛起来、和弦变亮;家长笑 | 家长参与点 |
| 7:00 | 家长打字说:"帮我们来一首恐龙派对",乐队 3~5 秒后切换成新风格;屏幕给出一句话 | LLM 的惊喜时刻(非阻塞,见 4.6) |
| 10:00 | 屏幕:"今天的歌存好了",孩子想再玩/想放给别人听 | **判断标准:不用大人催就继续**(6.2) |

### 画像 B:不懂音乐的成年人(假设,在家/办公室,独自玩)

- **想要:** 放松几分钟,验证"我是不是也能弄出点音乐"。**怕被当成要学东西。**
- **为什么会想玩:** 想看看 AI 能做到什么程度(好奇),同时不想被考。
- **为什么会想再玩:** 变成"下班后的 5 分钟情绪出口";每次说一句话就得到一个新乐队;存下的歌可以发给朋友。

| 时间 | 发生什么 | 关键点与风险 |
|---|---|---|
| 0:00 | 双击启动,灯亮,屏幕一句话:"按任意发光的键" | 不要教程 |
| 0:10 | 按键出声,乐队进场 | 怀疑:"是不是只是播背景?"——需让他感觉到**乐队在听你**(你停,它会变轻;你猛按,它会跟上) |
| 1:30 | 屏幕提示一次:"想要什么感觉?说一句话" ,他输入"下雨的咖啡馆",乐队变成慢速爵士钢琴 | 第一次惊喜。若 LLM 失败,必须诚实降级(4.7) |
| 4:00 | 他试"高潮"键、切乐器;开始"即兴" | 风险:5 分钟后新鲜感衰减,需要"进步感"(解锁新灯)来托住 |
| 8:00 | 乐队长说一句:"你一直在回到这个亮键,它是整首歌的家" | 轻量乐理,**只陈述观察到的事实** |
| 10:00 | 存歌,发给朋友 | **复玩动机弱是本画像最大不确定性**,靠次日回访验证 |

### 画像 C:聚会/家庭(假设 3~6 人,电脑接电视/大屏更好)

- **想要:** 一个大家围着、不用懂规则、能笑的东西。
- **为什么会想玩:** 门槛为零,**两个人可以同时在盘面左右两半一起"演奏",而 AI 乐队让两个人合起来也好听**;轮着按有"合奏"感。
- **为什么会想再玩:** "热场神器"——换风格、拉高潮、点歌(说一句话生成乐队)。

| 时间 | 发生什么 | 关键点与风险 |
|---|---|---|
| 0:00 | 设备放桌子中间,电视上显示大字+乐队卡 | 要有"一个操作员"管电脑,其他人只摸灯盘 |
| 0:30 | 第一个人按键,乐队进;第二个人加入 | 两人同时按,键位会冲突吗?主盘是同一个音阶,所以不冲突(设计上的好处) |
| 3:00 | 有人起哄:"来个海盗的!"→ 打字 → 乐队切换 | 这是"点歌"体验 |
| 6:00 | 一个人拉高潮,另一人换音色 | 聚会的"笑点"来自"一起把乐队弄疯" |
| 10:00 | 存一首"今晚合奏"的歌,放一遍回放 | **聚会风险:电脑和灯盘分两处**,必须有一人当操作员 |

> **三类共性假设:** 他们不想学规则,想马上有反应;会被"自己的动作改变了整个声音"打动,而不是被"自己创作的作品"打动。**这条假设决定了我们做"即兴乐队",而不是"作曲工具"**,要用第 6 节的测试验证。

## 3. 候选玩法(5 个,类型不同)

评估原则:先问**"AI 具体在做什么?拿掉 AI 会差在哪?"**;再看延迟、难度、风险。**不为技术亮点倒找用户价值。**

### 3.1 候选 A:随手乐队(AI 乐队即兴)——**即兴乐器类**

- **玩法:** 主盘是 5 音阶格子,按任意键都好听。你一按,AI 乐队(鼓手、贝斯手、和弦手)进场,并且**根据你的演奏动态调整**:你猛按,它们简化给你让路;你停下,它们填空、轻轻等你;你按"高潮"键,它们一起冲上去。一句话可换乐队风格。
- **AI/LLM/agent 的作用:**
  - **本地 agent(无 LLM,实时):** 鼓手/贝斯/和弦手三个带状态的小规则 agent,观察你最近几小节的"按键密度、音区、停顿",调整自己的演奏。这是毫秒级响应,**不可能走云端**。
  - **LLM(异步):** (1) 把一句话翻译成"乐队卡"(受控 JSON,白名单枚举);(2) 每隔若干小节,根据你的演奏摘要(几十字的文本)决定下一段怎么走、说一句话。
- **没有 AI 差在哪:** 只剩"一条固定伴奏循环"——像 Karaoke 背景,你的动作改变不了它,玩 3 分钟就腻;而且一句话换风格退化成"8 个预设"。**但诚实说:** 我的判断是"本地反应式 agent"贡献了大部分临场感,LLM 贡献的是"个性化和惊喜",**这两点各自值多少,必须用 6.2 的 A/B 实验量出来,不能拍脑袋。**
- **延迟:** 按键→声音是硬指标(目标 ≤40ms,拟定,**待测**)。LLM 不进这条链。
- **实现难度:** 中。引擎(音阶、节拍、鼓型、和弦)一个人 1 周可做;LLM 层 2~3 天。
- **风险:** (1) 声音延迟与音质(最大);(2) "好听但没成就感"、"代劳感";(3) 5 分钟后的新鲜感;(4) 乐队 agent 调得不好会"抢戏"或"掉线"。

### 3.2 候选 B:哼一句,变成网格乐曲——**输入转换类**

- **玩法:** 对着电脑麦克风哼一句或说一句旋律,系统识别音高、修正成一个调内的好听旋律,**让网格上相应键依次亮起并播放**;你再用手指"跟着亮的键"重弹,或叠加伴奏。
- **AI 的作用:** 主要是**音高检测 + 旋律量化**(信号处理/小模型,如 pYIN、CREPE、Basic Pitch `[待验证]`),不是 LLM。LLM 只能选风格、起名字,贡献偏弱。
- **没有 AI 差在哪:** 没有音高检测就没这玩法。AI 价值在于"把你的跑调哼唱修成好听",属于真实的 AI 作用。
- **延迟:** 离线处理即可(哼完 1~3 秒出结果),不需要实时。
- **难度:** 中高。麦克风环境噪声、小白"不准的哼"识别效果 `[待验证]`;把识别结果映射成网格上的键与节奏也要设计。
- **风险:** (1) 需要对着麦克风唱——**聚会/成年人会害羞**;(2) 小孩声音与噪声下识别不稳;(3) 隐私:麦克风是敏感数据,必须说明不上传;(4) 灯盘在这个玩法里只是"显示器",没发挥它的强项。
- **适合当:** 第二期的"魔法入口",不适合作为 MVP。

### 3.3 候选 C:跟着亮的键弹(AI 现场谱面)——**节奏/跟随游戏类**

- **玩法:** 像 Guitar Hero/Synthesia:一串"亮键"从盘面一端流向另一端(8 行刚好能做"来音预告"),你按亮的键,旋律就出来。**歌永远不停,你按对,旋律就多一层;按偏了,也不让你"失败"**,只是少一层。
- **AI 的作用:** AI 现场生成"谱面"——按心情卡生成原创旋律(约束为五声音阶 + 每小节节奏模板),再自动适配到网格上。LLM 可以起旋律草稿,**必须经本地校验器修正**(LLM 直接写旋律的准确度不可靠 `[待验证]`)。
- **没有 AI 差在哪:** 没有 AI,只能玩内置几首固定的谱;**也不能用别人的流行歌谱**(版权)。AI 价值是"无限的、原创的、符合你心情的谱面"。
- **延迟:** 谱面可预生成;但**判定(你按没按中)要求灯与声同步**,按键→灯反馈需非常快,否则"跟着亮"的游戏会显得"不准"。
- **难度:** 中高。节奏游戏的判定窗口、灯的刷新带宽、没有力度都不利。
- **风险:** (1) **这是"游戏",有判定就有失败**,与"不会错"冲突,要靠"不掉线"设计软化;(2) 灯盘刷新能力(整盘重绘频率)`[待验证]`;(3) 你要读灯而不是听,容易"盯灯弹",音乐性弱。
- **适合当:** 候选 A 里"带路灯"的轻量版本,而不是独立 MVP。

### 3.4 候选 D:一句话变乐器(心情→可玩配置)——**创作/配置工具类**

- **玩法:** 你说/打一句话("下雨的夜晚猫咖啡馆"),LLM 把它翻译成一整套可玩配置:音阶、速度、音色、鼓型、和弦进行、灯盘配色;灯盘立刻变成那个氛围的乐器。
- **AI 的作用:** **真正的语义理解 + 受控输出**:LLM 输出的是白名单内的枚举参数(例如 style ∈ {jazz, lofi, pirate…}),本地校验后才用。
- **没有 AI 差在哪:** 只剩"8 个预设主题",每个人听到的都一样。有了 LLM,任何一句话都能得到"差不多对味"的结果(**这个"对味"程度要靠盲听测试量化**)。
- **延迟:** 单次异步 2~5 秒 `[估算,未测]`,非阻塞即可。
- **难度:** 中。核心是设计好卡片 schema 与校验。
- **风险:** (1) 独立玩 5 分钟后就只剩"按键发声"(缺少乐队的动态);(2) 与市面上的"AI 作曲"同质;(3) LLM 输出不合法/不合适内容(尤其孩子场景)。
- **适合当:** 候选 A 的"开场魔法"。**单独不够当 MVP。**

### 3.5 候选 E:乐队学徒(渐进教乐理的闯关)——**学习类**

- **玩法:** 7 个小关,每关用游戏的方式让你体验一个概念:拍子(跟着呼吸灯按)、高低(哪个键更"尖")、**回家(主音)**、紧张与放松、大调/小调(换心情)、和声(哪些键"站稳")、休止(留白)。过关解锁新的灯与新的键。AI 教练会评语。
- **AI 的作用:** 本地"演奏分析"判定你是否做到了(比如你是否回到了主音);LLM 把评语说得更人话、个性化,**但评语必须只陈述观察到的事实**("你在 3 个小节里回到了亮的键")。
- **没有 AI 差在哪:** 没有 AI 就是固定教程,要么枯燥要么太难;AI 让难度自适应、评语不死板。但**教程本身是流程设计,不是 AI。**
- **延迟:** 本地分析实时;评语异步。
- **难度:** 中高(7 关内容设计工作量大,而且需要真人调试)。
- **风险:** (1) **"学东西"本身会劝退想玩的人**;(2) 评语稍有评价口吻就变成学校;(3) 作为首个体验太重。
- **适合当:** MVP 之后的"进步感"层,每次只解锁一个概念,不独立成关。

### 3.6 对比(1~5,5 最好;**主观判断,不是实测**)

| 维度 | A 随手乐队 | B 哼变乐曲 | C 跟灯弹 | D 一句话变乐器 | E 乐队学徒 |
|---|---|---|---|---|---|
| 10 秒内出声 | **5** | 3(要开口) | 4 | 3(要打字) | 4 |
| 不会错 | **5** | 4 | 3(有判定) | 4 | 3 |
| 小白第一次的惊喜 | **5**(乐队进场) | 4 | 3 | 4 | 2 |
| AI 不可替代性 | 4(本地 agent 反应 + LLM 个性) | 4(音高检测) | 3 | 3(LLM 配置) | 3 |
| 发挥灯盘的长处 | **5** | 2 | 4 | 3 | 3 |
| 孩子可独立玩 | **5** | 3 | 3 | 2(需打字) | 3 |
| 聚会友好 | **5**(多人互不冲突) | 2(害羞) | 4 | 3 | 1 |
| 1~2 周可做出 | 4 | 2 | 2 | 4 | 2 |
| **是否玩中学**(新增) | 4(循环/分层/和弦块都是动作) | 2 | 3 | 2 | 3(但容易变说教) |
| **灯光是否有趣**(新增) | **5**(节拍脉动/幽灵手指/涟漪/和声渐变) | 2 | 4(来音预告) | 3 | 3 |
| **创作感**(新增) | 4 | 4 | 1(跟着弹) | 3 | 2 |
| 复玩动机 | 3(**最大不确定**) | 3 | 4 | 3 | 4(但门槛高) |
| 断网可降级 | 4(预设卡+本地 agent) | 5(本地) | 4 | 2 | 4 |

### 3.7 MVP 选择:**候选 A「随手乐队」,把 D 当作开场魔法、C 的轻量版当作带路灯**

理由(按用户价值排序,不是按技术有趣度):
1. **第一个用户(孩子/成人/聚会)都能在 10 秒内出声。** B、D 需要说话/打字,E 要先学,C 要先读灯。只有 A 做到"拿起来就按"。
2. **"不会错"最彻底:** A 里没有判定、没有评分、没有失败。其他玩法至少有一环(开口、读灯、答题)可能让人尴尬。
3. **最好用到灯盘的长处,最少用到它的短处:** 灯盘擅长"确定位置的 64 个键 + 变色",不擅长"表现力与文字"。A 只需要前者。
4. **AI 的位置自然:** 本地 agent 解决"响应跟手",LLM 解决"个性化惊喜",两者各管一段,而不是把 LLM 硬塞进实时链。
5. **自带升级路径:** D(一句话)、C(带路灯)、E(解锁)、B(哼唱)都是后续可挂在 A 上的模块,不是推倒重来。
6. **聚会场景成立:** 多人同时玩不会互相破坏音乐——这是其他玩法给不了的。

**A 的最大风险要提前说清:** 它的"新鲜感能撑多久"没有任何数据。MVP 的任务之一就是用 6.2 的次日回访把这件事量出来;如果小白 10 分钟后就不想再玩,下一步优先加"进步感"(E 的轻量解锁)而不是加更多乐队。

## 4. MVP 详细设计:「随手乐队」

### 4.1 设计原则

- **亮的才能按,按了一定出声。** 不存在"没反应的键"(**诚实性:每次按键一定出声,不静默吞掉**)。
- **灯盘管"手感",电脑管"话"。** 灯盘做颜色/呼吸/闪烁;文字与语音在屏幕(灯盘只支持 ASCII 滚动文字 [MK2手册])。
- **一次只教一个动作。** 开场不弹教程;只做"呼吸提示"。
- **乐队听你的。** 玩家的音是主角,乐队是回应。
- **AI 只陈述观测事实,不替人下结论,不夸张捧场。** 例:"你一直在回到这个亮键"(事实);**不说**"你真有天赋""你一定很开心"。

### 4.2 按键映射(强制 Session 布局,通道 1)

启动时发 `F0 00 20 29 02 18 22 00 F7` 强制 Session 布局 [MK2手册·Layouts]。我们**不使用**设备上印刷的 Session/User 等出厂功能,一律按 CC/note 号处理。

**主盘 64 键 = 乐器(旋律区)**

- 音高规则(以 C 大调五声 C D E G A 为例;"调"由乐队卡决定):
  - 设行号 r(0=最靠近你的一行起,向外递增)、列号 c(0 起),**音级序号 n = c + r**(每上一行等于右移一格;**初值,上机/试玩后调**)。
  - n → 五声音阶中的第 n 个音(5 个音一个八度)。范围 n = 0..14,约 3 个八度,基准音 C4 附近 `[参数待调]`。
  - 好处:音高向右、向外都升高,**同一个音在盘面多个位置出现**,孩子手大够不着时总有别的位置;主音(1 级)在斜线上连成一条"回家线"。
- 颜色:同一个"音名"同一种颜色,所以盘面上是**斜向的彩色条纹**,看起来像一幅图而不是 64 个无差别的格子。主音用最醒目的暖白/橙色。
- **当前和弦的"稳定音"更亮**(随和弦变化),不稳定的音稍暗——不用任何文字,纯靠亮度表达"哪些键现在最稳"。

**侧列 8 键 = 乐队风格卡 S1~S8(note 19、29…89 `[待验证,需上机核对]`)**

| 键 | 功能 | 灯反馈 |
|---|---|---|
| S1 | 梦幻 | 各卡一种固定颜色,当前卡呼吸 |
| S2 | 欢快流行 | 同上 |
| S3 | 国风五声 | 同上 |
| S4 | 电子律动 | 同上 |
| S5 | 慢速爵士/咖啡馆 | 同上 |
| S6 | 海盗/冒险 | 同上 |
| S7 | 安静/夜晚 | 同上 |
| S8 | **"你说的那个"**(LLM 生成,没生成时灭或暗) | 新生成时闪烁一次,选中后呼吸 |

- 切换在**下一小节线**生效,淡入淡出(避免突兀)。S1~S7 卡 = 本地预制,**断网也可用**。

**顶排 8 键 = 控制 C1~C8(CC 104~111)**

| 键 | CC | 功能 | 灯反馈 |
|---|---|---|---|
| C1 | 104 | **视图切换:弹奏 ⇄ 编曲**(编曲视图见第 9.2 节) | 弹奏=常亮;编曲=呼吸 |
| C2 | 105 | **带路灯**开/关(AI 在盘面上用硬件呼吸灯提示"接下来这个键很好听") | 开=亮;关=暗 |
| C3 | 106 | **留住这一段**:把你刚弹的最近 4 小节变成一层循环(自动配一个新乐器) | 按下时整盘一闪,层颜色出现 |
| C4 | 107 | **撤掉最近一层**(再按一次可恢复) | 点按短亮 |
| C5 | 108 | **能量**:0 乐队休息 → 1 轻 → 2 中 → 3 高潮(循环) | 用 0~3 档亮度表达 |
| C6 | 109 | **换乐器**(旋律音色在 4 个里切;录过声音后多一个"我的声音") | 点按短亮 |
| C7 | 110 | **叫乐队长**(屏幕出现输入框:"说一句话,乐队就换") | 等待回应时呼吸 |
| C8 | 111 | **存下这首歌** | 保存成功后绿闪 |

- 速度由乐队卡和能量档决定,**不给玩家单独的快慢键**(减少无谓选项)。
- **控制键 8 个已用满,后续任何新功能都要先换掉一个。**
- **工期诚实说明:** 加入"留住这一段/编曲视图"后,5.6 的 1~2 周只覆盖"弹奏 + 乐队 + 灯光 + 预制卡";完整创作闭环按 3~4 周估(估算,未验证)。
- **按到没有功能的键?** 不存在——所有键都有功能。上机核对缺角键帽对应的键编号,必要时避开(README:有缺角)。

### 4.3 乐队卡(Band Card)——整个产品的"数据单位"

一张卡 = 一支乐队的完整描述,受控 JSON,**LLM 只能从白名单里选**,不能自己造参数。

```
{
  "name":     "下雨的咖啡馆",            // 屏幕显示,长度限制
  "key":      "C" | "D" | ... 12 个,      // 调
  "scale":    "major_pent" | "minor_pent" | "guo_feng_pent" | ...,  // 白名单
  "bpm":      60..140,
  "progression": ["I","vi","IV","V"],     // 取自"已验证和弦进行库",不接受自由和弦
  "drums":    "lofi_01" | "pop_02" | ..., // 取自鼓型库
  "bass":     "root_fifth" | "walking" | ...,
  "chords":   "pad" | "arp" | "comp",
  "voices":   {"melody": GM号白名单, "bass": ..., "chords": ...},
  "palette":  色卡 id,                    // 灯盘配色
  "comment":  "一句话说明"                // 长度限制,过内容过滤
}
```

**入库门槛(自动检查,可测):**
- 网格上所有音高 × 该卡每个和弦,无"和弦音小二度/小九度冲突"(见 1.2)。
- 所有枚举字段在白名单内,数值在范围内。
- 孩子场景:`comment`、`name` 过关键词+长度过滤。

### 4.4 灯怎么反馈(一个孩子能看懂的)

| 事件 | 灯 | 备注 |
|---|---|---|
| 按下某个键 | **该键立刻亮白,再退回本色**(本地,在发声指令的同一时刻发出) | 是"我按了"的最直接确认,目标 ≤30ms(拟定,待测) |
| 和弦变化 | 当前和弦的"稳定音"整体变亮一点 | 一次 SysEx 批量刷新,**只刷变化的灯**,降低 USB 压力 |
| 带路灯(C2 开) | 一个建议键**用硬件呼吸灯**提示(SysEx 28h,调色板号)[MK2手册·Pulse] | 不占实时带宽;每次只提示 1~2 个,避免满盘闪 |
| 节拍 | 盘面上所有"主音键"用硬件呼吸灯随拍脉动(用 MIDI 时钟 F8 给硬件定速)[MK2手册·MIDI Clock];详见第 10 节 | 让人"看见"节拍 |
| 乐队切换 | 盘面配色渐变成新调色板 | 配色用 RGB;**注意闪烁/呼吸只支持调色板号**,色卡要选"在调色板里有对应号"的颜色 `[待上机对色]` |
| 没连接/没声音 | 盘面所有灯做"慢呼吸" + 屏幕提示 | 绝不假装一切正常 |

**颜色亮度控制在中等**(不开到最亮),原因:孩子眼睛舒适;整盘全亮时 USB 供电是否受影响 `[待验证]`。

**"没有力度"变成设计特性:** 软件根据"节拍位置 + 是否和弦音 + 离上次按键的间隔"赋予一个 40~110 的力度值——重拍重一点、快速连按渐弱、和弦稳定音略重。**这样同样的按压听起来有"人味"**,而不是每个音一样硬。

### 4.5 "30 秒上手"

| 秒 | 灯盘 | 屏幕 / 声音 | 状态 |
|---|---|---|---|
| 0~3 | 自检:亮暖色波纹从中心扩散,变成盘面配色 | 大字"随手乐队" | 本地 |
| 3~8 | **一个键(主音)在呼吸** | 大字"按一下发光的键" | 本地 |
| 8~12 | 玩家按:键亮白,**出一个钢琴音**,呼吸点转移到邻近一个键 | "再按几个" | 本地(即时) |
| 12~20 | 玩家按到第 3 个键 → **下一小节线,鼓+贝斯+和弦一起进来**,盘面稳定音变亮 | "乐队来了!" | 本地 |
| 20~30 | 玩家自由按;侧列 S1~S8 的颜色出现 | "按侧面的颜色,换一支乐队" | 本地 |

**如果 15 秒内没人按任何键:** 呼吸点加快,屏幕大字重复;45 秒仍没人按 → **自动演示**:灯盘自己"弹"一小段旋律,让人看到"这个键会出声"。**绝不弹出长文字说明。**

### 4.6 "不会错"机制(汇总)

1. **音高:** 盘面只有五声音阶音(1.2)。
2. **和声:** 乐队只用通过自动检查的和弦进行(4.3)。
3. **时间:** 鼓/贝斯恒稳;玩家的音**不做延后量化**(保证手感),只回放时量化(P1)。
4. **密度:** 乱按时**不静音玩家的音**(否则等于欺骗)。改为:自动缩短音符长度、限制同时发声数(复音上限)、让乐队简化让路。
5. **音区:** 最高与最低位置的音略轻,避免尖叫或浑浊。
6. **力度:** 软件赋予(4.4)。
7. **安全网:** 若检测到"盘面静止 + 乐队在放"超过 N 秒,乐队**柔和减轻**而不是继续大声(避免一个人走开乐队狂响)。

### 4.7 AI 的调用时机(必须本地 vs 可异步)

| 事件 | 在哪 | 目标延迟(拟定,待测) | 说明 |
|---|---|---|---|
| 按键 → 出声 | **必须本地** | ≤40ms | 整条链:USB MIDI → 引擎 → 音源 → 声卡;**LLM 绝不在链上** |
| 按键 → 亮灯 | **必须本地** | ≤30ms | 同上 |
| 乐队 agent(鼓/贝斯/和弦)调整 | **必须本地** | 每小节决策一次 | 规则 + 小状态机 |
| 节拍时钟 | **必须本地** | 抖动 <5ms `[待测]` | 以音频/调度器时钟为准,不能随主线程卡顿而漂 |
| 侧列切换乐队卡 | **必须本地** | 下一小节线生效 | 预制 7 张本地卡 |
| 带路灯推荐"下一个键" | 本地规则 | 小节边界更新 | 规则:靠近当前音、落在稳定音、避开刚用过的音 |
| **"说一句话"→生成乐队卡** | **异步 LLM** | 目标 ≤5s,**硬超时 6~8s**(拟定,未测) | **不阻塞演奏**:继续用旧乐队,生成好了在下一小节线淡入 |
| **乐队长每 ~16 小节点评/建议** | **异步 LLM** | 同上 | 输入是玩家行为摘要(例:按键数、音区分布、是否回到主音、停顿次数),**不是音频**;输出为受控 JSON(下一段能量/一句话) |
| 存歌后的命名、简评 | 异步 LLM | 可慢 | 失败则用模板 |

**LLM 的输入只有:用户打的一句话 + 行为摘要文本。** 不上传音频、不上传按键时间戳全量(只传统计)。

**乐队长说话的文案红线:**
- 只陈述观察:"这一段你多按了高音那边。"
- 不推测动机、不评价人("你是不是累了""你真棒")。
- 无网/LLM 失败时**如实说**:"乐队长现在没联网,我们先用现成乐队。"**不得假装 LLM 在回应。**

### 4.8 渐进"悄悄教乐理"(MVP 只做第一档)

| 档 | 条件(由本地演奏统计触发) | 解锁 | 乐队长的一句话(示例,必须是事实陈述) | MVP? |
|---|---|---|---|---|
| 0 | 初始 | 五声音阶 + 稳定音变亮 | — | ✔ |
| 1 | 累计演奏 ≥N 分钟 | **"回家"提示**:乐队偶尔留一个小节空拍,主音键呼吸 | "这个键是这首歌的家" | P1 |
| 2 | 回到主音 ≥N 次 | 解锁 2 个"带点紧张"的音(暗色键) | "这两个键听起来有点悬" | P1 |
| 3 | 使用过切换风格 | 展示"大调/小调"对照(同一旋律两种情绪) | "同样的键,换了乐队感觉不一样" | P2 |

目的:**让玩家觉得"我在变强",而不是"我在被围起来"。** 同时回应 1.2 里"限制太多会无聊"的风险。

### 4.9 没网降级(诚实分级)

| 级别 | 条件 | 能玩什么 | 对用户说的话 |
|---|---|---|---|
| L0 | 正常 | 全部 | — |
| L1 | LLM 超时/偶发失败 | 仍可玩;一句话请求用**关键词匹配本地卡**("海盗"→S6)返回最近一张,并明确说明 | "我没能生成新的,先给你最近的一支。" |
| L2 | 完全无网 | 7 张本地乐队卡 + 本地 agent + 带路灯 + 存歌;侧列 S8 灭 | "乐队长没联网,只能用现成乐队。" |
| L3 | 灯盘未连/被占用 | 屏幕提示排查:检查 USB、关闭其他占用 MIDI 的软件(例如 Ableton、Novation Components)`[待验证端口独占行为]` | "没找到灯盘。" **不给假界面** |
| L4 | 音源不可用 | 屏幕提示"没有声音输出,检查音箱/驱动";灯盘继续亮 | 不假装在出声 |

## 5. 技术方案草图(一个人 1~2 周)

### 5.1 分层

```
┌──────────────┐   MIDI in/out   ┌──────────────────────────────┐
│ Launchpad    │ ◄────────────► │ ① MIDI 输入输出层               │
│ Mini MK2     │                 │  (mido + python-rtmidi)         │
└──────────────┘                 └───────────────┬────────────────┘
                                                  │ 事件:pad 按下/松开(行,列)、控制键
                                  ┌───────────────▼────────────────┐
                                  │ ② 音乐引擎(本地,实时)            │
                                  │  音阶/键位映射 | 和弦进行 | 鼓型 │
                                  │  节拍时钟 | 乐队 agent | 力度赋予│
                                  └───┬─────────────┬──────────────┘
                     note events     │             │ LED 指令
                     ┌───────────────▼──┐   ┌──────▼───────────────┐
                     │ ④ 音源后端接口    │   │ 灯光渲染器(只刷变化)│──► 回到①
                     │ (可切换)         │   └──────────────────────┘
                     └───────────────────┘
                                  ▲
                    乐队卡 JSON    │  行为摘要
                                  │
                       ┌──────────┴──────────┐
                       │ ③ AI 层(异步)       │
                       │ LLM 客户端 + 校验器   │
                       │ + 预制卡库 + 降级     │
                       └─────────────────────┘
          屏幕:tkinter 小窗(Python 自带)——大字提示/乐队长一句话/输入框/状态
```

### 5.2 ① MIDI 输入输出层
- **库:** `mido` + `python-rtmidi`(用户已确认可用;**本机当前未装 mido,原型第 1 天安装,见第 7 节待确认**)。
- 开 `Launchpad MK2` 的 IN/OUT 端口 [README·实测];端口名在 Windows 上可能带序号后缀 `[待验证]`,按"名字包含 Launchpad"匹配。
- 回调线程只做"解析 + 推入线程安全队列",**不在回调里做重活**。
- 启动流程:`Device Inquiry`(F0 7E 7F 06 01 F7)确认身份 [MK2手册·Device Inquiry] → 强制 Session 布局 → 全灭 → 开场动画。**退出一定发"全灭"。**
- 灯刷新:所有灯变化合并成**一条 SysEx(RGB,最多 80 灯)** [MK2手册·RGB Mode],而不是 64 条单灯消息。**USB 实际可承受的刷新速率 README 里写的是老型号数据(~400 条/秒),不能直接用,必须上机实测。**
- 没有力度(见 0.1#2),按下统一当"事件",力度在引擎层赋予。

### 5.3 ② 音乐引擎
- **全部本地、纯 Python 即可,自己写不到 500 行**,需要的是设计,不是库:
  - **键位映射:** (行,列) → 音级序号 → MIDI 音高(随乐队卡的 key/scale 变)。
  - **和弦进行:** 罗马数字 → 具体音(与键对应)。
  - **鼓型/贝斯型:** 16 步的数组(固定数据),按"能量档位"挑变体。
  - **节拍时钟:** 单独线程 + `time.perf_counter()`,**提前几十毫秒调度**(look-ahead);Windows 默认定时器精度较粗(约 15.6ms)`[待验证]`,可用 `timeBeginPeriod(1)` 或让**音频后端的时钟**当主时钟(见 5.5)。
  - **乐队 agent:** 滑动窗口统计(按键数/秒、平均音区、最近停顿)→ 三条规则调节三位乐手(4.1 / 4.7)。
  - **力度赋予、音符长度/复音上限**(4.4、4.6)。
  - **会话记录:** 记录所有 note 事件到 MIDI 文件(用 mido 即可),给"存歌"用。
- **可借用的现成库:** `mido`(MIDI 文件与消息);**不建议**用重型作曲库(music21 等)——体积大、与实时无关 `[待验证]`。

### 5.4 ③ AI 层
- **LLM 客户端:** 任何兼容 HTTP 的 LLM API,**供应商待定**(见开放问题)。**强制 JSON 输出 + pydantic(或手写)校验**,不合格重试 1 次,仍失败就降级。**LLM 绝不直接发 MIDI 或控制灯。**
- **两个 prompt:**
  1. `一句话 → 乐队卡`:提示里给白名单枚举与已验证和弦进行库,要求只输出 JSON。
  2. `行为摘要 → 下一段计划 + 一句话`:同样受控。
- **缓存与限额:** 同一句话缓存;每设备每日上限(默认值待用户定)。
- **本地回退:** 关键词匹配 7 张预制卡;模板化一句话。
- **隐私:** 上云的只有"用户打的一句话"和"行为统计摘要"。首次启动必须明说,可一键切离线。

### 5.5 ④ 音源——**选哪个,为什么**

| 选项 | 优点 | 缺点 / 未知 | 评估 |
|---|---|---|---|
| **Microsoft GS Wavetable Synth**(Windows 自带,GM 128 音色)| **零安装、零下载**,是 MIDI 输出设备,与引擎的"发 note"接口天然一致,Day 1 就能出声 | **音质:** 基于 Roland GS 采样的小型 DLS 音库,**音色偏"老 MIDI 铃声"**,鼓和钢琴够用但缺少现代感 `[待验证:依据是我对它的一般印象,没有本机试听]`;**延迟:** 业界普遍反映它**延迟偏高、不稳定**(经验值几十到上百毫秒)`[待验证,没有本机实测]`;Windows 新版 MIDI 服务是否改善 `[待验证]`;能否多程序同时打开 `[待验证]` | **适合当"保底"和 Day 1 冒烟**,不应作为最终体验方案 |
| **FluidSynth + SoundFont(SF2)** | 开源软合成器,直接加载 SF2;**音质取决于所选音色库**(GeneralUser GS 等许可相对宽松 `[待验证]`);可通过 pyfluidsynth 在进程内调用,并用其自带音序器调度 `[待验证 Windows 部署]` | 需要装 FluidSynth 的 Windows 库和一份 SF2;音频驱动选择(WASAPI/DirectSound 等)对延迟影响大 `[待验证]` | **推荐的正式方案**,但**必须先做延迟实测再拍板** |
| **自己做"采样器"**(预渲染音符 WAV + `sounddevice` 回调混音)| 完全控制延迟与音色,可以把"钢琴一个音"变成最低延迟路径 | 需自己写混音器、处理复音与淡出;多一点工程量 | **后备**:如果 FluidSynth 延迟不达标 |
| 虚拟 MIDI 线(loopMIDI)+ VST 宿主 | 音质可以非常好 | 对小白要装一堆东西,违反"零配置" | **不选** |

**推荐路线(两阶段):**
- **Day 1~3:先用 GS Wavetable 打通整个链路**,所有发声走一个 `SynthBackend` 接口(`note_on/note_off/program_change`),这样换后端不改引擎。
- **同时做延迟实测(见下)。**
- **Week 1 末:换成 FluidSynth+SF2 对比,选延迟最低且音质可接受的作为默认**。GS Wavetable 保留为"没装音源也能出声"的保底(L4 提示"当前音源是基础版,音质一般")。

**延迟实测方法(必须做,没做之前所有延迟数字都是拟定):**
- **端到端:** 用手机 240fps 慢动作录像,同时拍到"手指按下"和"音箱声音波形/灯"。或:程序在收到 pad note-on 的**同一刻**往日志写时间戳,并在耳边放麦克风录音,对比音频起点(粗)。
- **分段:** USB 往返(程序 ping 灯盘的"点灯"与"收到按键"对比,**这部分我们没有数据**)、引擎处理、音源缓冲。
- **判断线(拟定):** 端到端 ≤40ms 属"跟手";40~80ms 属"能接受但能感觉到";>80ms 属"不跟手,弹快会乱"。`[该阈值为一般音乐软件经验,未核实;以真人测试为准]`
- 若 GS Wavetable 端到端 >80ms,MVP 就**不能**把它作为推荐配置。

## 6. 验收:怎么用真人小白测

### 6.1 测试设计(拟定样本,不是统计显著)
- **人数:** 孩子 4(带家长)、成年小白 4、聚会组 1~2 组(每组 3~5 人)。样本太小,只用于**发现问题和排序**,不用于下"可以上线"的结论。
- **筛选:** 不会乐器、不系统学过乐理;(可以有 1~2 位会乐器的做对照,看"专业人士是否觉得太幼稚"。)
- **流程:** 观察员不教学、不暗示;只说"这是个能出声音的玩具,你随便玩"。**计时 10 分钟后问问卷;次日回访(电话/消息)。**
- **会话日志:** 程序自动记录(按键时间、控制键使用、LLM 请求/失败、卡顿事件);**只存本机,事后经同意才分析。**

### 6.2 指标(目标值都是拟定验收线)

| 指标 | 怎么量 | 拟定验收线 | 解读 |
|---|---|---|---|
| **首次出声用时** | 日志:从"设备交给用户/程序启动"到第一次 note 发声 | 中位数 ≤10s | 卡在这里说明引导不够 |
| **乐队进场用时** | 日志:到第一次乐队进场 | ≤30s | |
| **"我弹出了好听的东西"自评** | 5 分钟、10 分钟各问一次,1~5 分 | 10 分钟时中位数 ≥4 | |
| **"是你弹的还是电脑弹的?"** | 开放式 + 打分(1=全是电脑,5=全是我) | 中位数 ≥3.5 | **用来监测"代劳感"** |
| **愿意再玩** | 10 分钟后问:"如果明天还在桌上,你会再玩吗"(是/否/不确定)+ **次日回访是否主动玩过** | 是 ≥60%,次日主动玩过 ≥30% | **次日行为比口头意愿可信** |
| **发现控制键用时** | 日志:首次按到侧列风格键/高潮键的时间 | 3 分钟内 ≥70% 发现 | 说明"侧列有颜色"这个暗示是否有效 |
| **空闲/卡住** | 日志:连续 20 秒无任何按键 | 次数和时机作为问题清单 | |
| **LLM 一句话"对味"** | 盲听:同一句话,用 LLM 卡 vs **随机选一张预制卡**,问"哪个更符合这句话" | LLM 胜率 >60% 才算 LLM 在起作用 | **没过说明 LLM 层该砍或重做 prompt** |
| **本地 agent 是否有用** | A/B:乐队会根据你的演奏变化 vs **固定循环伴奏**,问"哪个更像在和你一起玩" | 反应式胜率 >60% | **这是对"AI 真有用"最关键的证据** |
| **延迟感受** | 开放问"按下和出声合拍吗" + 实测数 | 数值见 5.5 | |
| **玩中学(新增)** | 玩完 10 分钟后,**先让玩家自由说"你发现/学到了什么"**,不给选项、不提示;两位观察员独立把回答对到第 1.4 节的概念表 | ≥50% 的人能自发说出 ≥1 条**正确**规律(例:"停在亮键上像结束""加一层就丰满""换风格情绪变了")| 说不出=机制没被发现,不是人笨;看日志里谁没碰到对应操作 |
| **灯光乐趣(新增)** | 问"哪个灯光效果你记得/喜欢";日志:玩家是否看灯(静音试玩 1 分钟对照:关声音只看灯,玩家还愿不愿意按) | 静音试玩仍有 ≥50% 愿意继续按 | 灯是玩法一半的证据 |
| **灯光安全(新增)** | 自查脚本:任何灯效不得出现大面积 >3 次/秒闪烁(参考 WCAG 2.3.1 三次闪光阈值 `[待验证]`) | 100% 通过 | 孩子与光敏人群 |

### 6.3 已知限制(提前写明)
1. **无力度:** 无法表现轻重,只能靠软件赋予,**不能称为"有表现力的乐器"**。
2. **无屏幕/无声音/只 ASCII 文字:** 必须依赖电脑屏幕和音箱,不是"拿起来就能独立玩"的玩具。
3. **音高被限制:** 小白开心,但**想弹出自己知道的歌的人会失望**;"随便弹都好听"和"弹出我想要的"是两件事。
4. **音质与延迟取决于 Windows 音源:** 保底方案(GS Wavetable)可能"能玩但不惊艳"`[待测]`。
5. **LED 刷新能力、USB 吞吐、键位编号(侧列)都待实测。**
6. **文化偏向:** 默认流行/五声,对其他风格体验未知。
7. **缺角键帽:** 可能影响个别键的手感,需上机逐键核实 [README]。
8. **LLM 依赖网络与厂商,内容安全对孩子要额外把关。**
9. **没有做任何真人调研,所有判断为假设。**

## 9. 创作闭环与"歌"的数据模型(玩中学的载体)

### 9.1 玩家视角:一首歌是怎么搭出来的(不出现任何术语)

1. **按键即兴**(弹奏视图):乐队进场,你弹的每个音都被记下来。
2. **留住这一段(C3)**:盘面上你刚才弹的那几小节,**变成一个会自己重复的"幽灵手指"**(同一批键按顺序自己亮起、自己发声)。系统自动给它配一个新乐器、新颜色。 → 玩家发现:**"重复一段就成了循环乐句"**。
3. **再弹、再留住**:每一层一个乐器、一种颜色,盘面逐渐变成多色交织的"光织物"。 → **"加一层就多一个乐器"**。
4. **编曲视图(C1)**:盘面变成"8 小节时间轴":列=第几小节,行=几个和弦色块。按一格=这一小节用这个和弦;播放头(一列亮光)从左向右扫过。 → **"按下的组合自动变成和弦进行"**。
   - 乐队长可用"呼吸灯"提议一种排法("试试这样?"),玩家按一下接受或自己改。
   - 玩家也可以只用它,不碰旋律(孩子会把它当"涂色块")。
5. **存下这首歌(C8)**:得到一个自己的作品。

### 9.2 编曲视图键位(MVP 草案)

| 区域 | 含义 |
|---|---|
| 主盘第 1~8 列 | 第 1~8 小节(播放头从左向右) |
| 主盘第 1~6 行(按行号从近到远) | 6 个和弦色块(进行库里的 6 个,例:I ii iii IV V vi,**仅限已通过 4.3 自动检查的和弦**);第 0 行 = 该小节"留白" |
| 主盘第 7 行 | (预留)**段落标记**:为一小节加"能量上扬" |
| 侧列 S1~S8 | 仍是风格卡,切换后和弦色块颜色、配色整体换 |
| C1 | 回到弹奏视图 |

### 9.3 "歌"的内部模型(agent 调用的对象)

自研**工程模型**(JSON 文件,本机存储),不依赖任何第三方 DAW:

```
Song {
  card: BandCard,                     // 风格/调/速度/和弦进行/音色(见 4.3)
  progression: [chord x 8 小节],      // 编曲视图的结果
  layers: [ { instrument, color,      // 每一层 = 一个循环乐句
              events:[(拍位,音级,时长)],
              source:"play"|"agent"|"recorded_sample" } ],
  energy_curve: [...],                // 能量档随小节
  lights: [light_cue, ...],           // 灯光脚本(第 10 节)
  samples: [用户录的声音,见第 13 节]
}
```

- **通用格式导出:** 标准 MIDI 文件(`.mid`)+ 离线渲染的 WAV(用内置音源渲染)。这就是"可保存/分享"的全部要求。
- **Agent 的工具(内部函数,白名单+校验):** `set_card`、`set_progression`、`add_layer`、`suggest_next_key`、`set_energy`、`light_cue`、`save_song`。**没有"删除用户歌曲"这个工具**;改动先在副本上做,玩家一键撤销。工具 schema 可按 MCP 风格定义,将来方便别的 agent 接入,但**当前不依赖 MCP**。
- Agent 只能改"当前这首歌"的内存模型,**不碰用户其他文件**(权限最小)。

## 10. 灯光设计(灯光是玩法的一半)

### 10.1 约束(先说清能做什么)

- 一条 SysEx(RGB 0Bh)最多 80 灯 [MK2手册·RGB Mode]:整盘一帧约 264 字节(估算:64×4+8)。USB 实际能持续刷多快,**手册没写;README 里"~400 条/秒、整盘 200ms"是老型号数据,不能采用 → Day 1 必须实测**:连续发满帧,看多少帧/秒后开始丢灯或影响按键回传。
- **硬件自己会做的动画不占带宽**:闪烁(SysEx 23h / 通道 2)、呼吸(SysEx 28h / 通道 3)、节奏跟 MIDI 时钟 F8(24/拍,40~240BPM) [MK2手册·Flashing/Pulsing/MIDI Clock]。**但它们只用调色板号(128 色),不是 RGB。**
- 灯只写不读;滚动文字只有 ASCII。

### 10.2 三层灯效(高层永远不被低层挡住)

| 层 | 内容 | 谁产生 | 响应要求 | 带宽策略 |
|---|---|---|---|---|
| **L1 必须即时** | **按键反馈**:按下的键立刻亮白,再退回本色;松开后留一个短拖尾 | 本地引擎,与按键事件同一时刻 | ≤30ms(拟定,待测) | **用 3 字节单灯 note-on,不排队**;**宁可丢装饰帧,也不让按键反馈等待** |
| **L2 跟随节拍** | ① 主音键随拍脉动(硬件呼吸 + F8);② 小节线:当前和弦的稳定音整体提亮一档;③ **和声变化时配色渐变**(下一和弦色 4~6 帧淡入);④ 编曲视图的**播放头**;⑤ **幽灵手指**(已留住的循环按键序列在盘面上自己亮起,各层不同色) | 本地调度器,与音频时钟同源 | 对拍误差 <1/16 拍(拟定) | 只刷**变化的灯**;渐变限制步数;批量 SysEx |
| **L3 AI 生成/编排** | **灯光"表情"与脚本**:乐队长按卡/段落选的灯效(扫光、涟漪、呼吸色环、星点);鼓手的踢/军鼓/镲分别驱动不同区域的闪动;贝斯音驱动低音区"暗光涌动";能量档决定饱和度与动画密度;换乐队时的转场 | **LLM 只能从"灯效库"里选并填参数(JSON 白名单)**,本地渲染器执行 | 非实时,提前几小节排好 | 最低优先级,忙时降帧/降密度 |

### 10.3 具体灯效清单(玩家看得见的趣味)

| 灯效 | 对应音乐含义 | 层 |
|---|---|---|
| **音高 → 颜色**:同一音名同一色相;八度 → 亮度 | 音名(玩中学:同色键=同一个音) | 静态底色 |
| **按键涟漪**:按下后以按键为中心向外 1~2 圈渐暗扩散(每帧只改很少的灯) | 声音"扩散" | L1→L3 |
| **演奏轨迹拖尾**:最近 3~5 次按键留下渐暗的尾巴 | 旋律线可视化(看见"上行/下行") | L1/L2 |
| **节拍脉动**:主音键呼吸 | 拍子 | L2 |
| **和弦渐变**:每次和弦换,背景色在一小节内渐变到新和弦的色调 | 和声色彩 | L2 |
| **幽灵手指**:循环层自己亮起 | 循环/分层 | L2 |
| **鼓手表情**:不同鼓件闪不同区域 | 鼓型 | L3 |
| **能量**:档位越高,色越饱和、拖尾越长、涟漪越多 | 力度/张力 | L3 |
| **乐队长转场**:换风格时从中心向外一圈扫光 | 段落转换 | L3 |
| **留白提示**:能量 0 时盘面整体放慢呼吸 | 休止 | L3 |

### 10.4 灯光安全与降级
- **光敏安全:** 大面积灯不得每秒闪 3 次以上(WCAG 2.3.1 "三次闪光"阈值 `[待验证]`);自动检查脚本放进"灯效入库"流程,LLM 产生的灯效也要过。
- **亮度**中等,避免整盘全白(舒适 + USB 供电是否受影响 `[待验证]`)。
- **刷新降级:** 若检测到灯盘回传延迟变大(按键事件间隔异常/积压),渲染器自动关掉 L3、降低 L2 帧率,**保证 L1**,不报错、不假装。
- 灯光脚本只描述"灯",**LLM 永远不直接发 MIDI/SysEx**。

### 11.2 每次启动的自动流程

### 11.3 已知真实故障必须内置处理(来自本仓库实测记录)
- **VMware USB 仲裁器抢占设备**:[README] 记录首次插入被 `vmusb`(VID_0E0F)接管 → 错误码 43;并出现过 `VID_0000 描述符请求失败`;本机确实装有 VMware Workstation 17.6.3(见 0.0)。
  - **检测:** 枚举 USB 设备树,看 `VID_1235&PID_0069` 是否出现且有问题码,或设备被识别为 `VID_0E0F`。
  - **处理(分级,每一步需玩家同意):** ① 建议"拔掉重插";② 提供"一键修复"——请求管理员权限,把 `VMUSBArbService` 设为手动并停止(README 里的做法),**只做这一件事,并告知这是 VMware 的服务**;③ 仍不行,指向"使用说明"。
  - **红线:** 不静默改系统服务;不卸载用户软件;不强杀进程。
- 其他:端口名在 Windows 上带序号后缀、MIDI 端口是否独占 `[待验证]`。

### 11.4 AI agent 的"大白话修复向导"
- **诊断是结构化数据(规则产生)**:`{灯盘端口, 驱动状态, 问题码, 占用者进程, 音频输出设备, 网络}`。
- **文案由模板 + 可选 LLM 润色**;**无网或 LLM 失败 → 全部用模板**,功能不变,只是不那么口语。
- **LLM 不被允许执行任何系统命令**;"修复动作"只能是白名单函数(重试连接、打开设置页、请求管理员权限做上述一项修复),**每次都先问玩家**。
- 文案红线:只陈述观测到的事实("我看到灯盘被 XX 占用"),不推测原因("你是不是忘了关"),**做不到的就说做不到**。

### 12.3 许可证类型对"打包分发"的速查(`[待验证,以原文为准;非法律意见]`)
- **CC0 / 公有领域**:无义务,最安全。

- **CC-BY**:可商用,**必须署名**(放"关于/致谢"页并随安装包附许可文本)。
- **CC-BY-SA**:衍生品需同协议共享。**采样音色打进软件是否构成衍生品有争议 → 首发避开。**
- **CC-BY-NC**:非商用,**不进商用包**。
- **LGPL**:动态链接可商用,需提供替换途径;**GPL**:链接即传染,**避开**。

## 13. 用户自己录音 → 变成可弹的乐器

### 13.1 小白视角(2~3 分钟,"创作感 + 玩中学"的强化点)

1. 乐队长(屏幕 +可选语音)问:**"想不想用你自己的声音当一个乐器?"**(可跳过)
2. **"先拍一下手"**——屏幕波形实时跳动,拍完立刻变成**一个鼓点**:灯盘上点亮一个键,按一下就是你的拍手声。
3. **"再哼一个'啊——'"**——系统听出你哼的高低,**自动调到当前乐队的调内**,整盘变成"你的声音琴":往一个方向按是低的你,往另一个方向是高的你。
4. **"敲一敲杯子/桌子"**(可选)→ 变成第二种鼓/打击音。
5. **鼓手 agent 用你拍的手当"军鼓"**,你自己的声音出现在乐队里。
- **玩中学藏在这里:** 声音的**高低**(同一个声音按不同位置变高变低)、**节奏**(把拍手排进节拍)、**音色**(同一个键,杯子和手的音色不同)。
- **创作感:** "这是我的声音做的乐器",所有权感强,最容易被拿去分享。

### 13.2 大白话引导(以规则为主,LLM 不是必需)

| 阶段 | 系统怎么做 | 说什么 |
|---|---|---|
| 录前检查 | 采 1 秒背景噪声,算信噪比与削波 | 太吵:"这里有点吵,走近一点或换个安静的地方" |
| 录音 | 检测起音;每次录 2~3 秒;同一素材要 2~3 次 | "再来一次,我取最清楚的那次" |
| 质量判断 | 音量过小/削波/时长异常/杂音比 | 只陈述观测:"这次声音有点小";**不评价人** |
| 处理 | 裁头尾、轻降噪、归一化、淡入淡出(防爆音)| 玩家不看到技术细节 |
| 试听 | 立刻把声音映射到盘面 | "试试按这几个键" |

### 13.3 自动处理流水线与现成库(都需核实 `[待验证]`)

| 环节 | 做法 | 现成库(出处与许可待核)|
|---|---|---|
| 录音 | 系统默认麦克风 | `sounddevice`(MIT,PortAudio 封装)|
| 裁剪/静音检测 | 能量阈值或 `librosa.effects.trim` | librosa(ISC)或纯 numpy |
| 降噪 | 门限/谱减法(轻量,宁可保守)| `noisereduce`(MIT)或自写;**不做重降噪以免"水声"** |
| 起音/切片 | 按"敲/拍"自动切 | librosa onset(ISC);**避开 aubio(GPL-3)** |
| **音高检测** | 单声部:pYIN/YIN;更稳:CREPE | librosa `pyin`(ISC)、CREPE(MIT,依赖重)、Basic Pitch(Spotify,Apache-2.0,可输出 MIDI)|
| 调到调内 | 算偏差(音分),就近取**当前音阶内**最近的音;偏差不大时用**重采样**改音高(同时改速度,像采样器)| 自己实现;**Rubber Band 为 GPL/商业双许可,避开** |
| 多采样 | 让玩家哼"低/中/高"3 个音,各管盘面一区,避免"花栗鼠声" | 自己实现 |
| 映射成乐器 | 有音高 → 沿音级排布到网格;无音高(拍手/杯子)→ 作为鼓/打击,挂给鼓手 agent | 自己实现 |

**可行性判断(没做过实验,不下结论):**
- 单声部哼唱的音高检测是成熟做法;**成人较稳,孩子声音、噪声环境、气声要实测** `[待验证]`。
- "长音哼唱 → 重采样改高低"会改变时长与共振峰(变声感),所以让玩家录 3 个音高是更稳的做法;是否好听要盲听验证。
- 打击声(拍手/杯子)基本稳定,**这条路风险最低,最先做**。

### 13.4 隐私与诚实
- **录音只存本机,不上传**(除非玩家另行主动同意,二期才考虑);**不上传给 LLM**(LLM 只收到"录了几个、音高大概多少"这样的统计)。
- 孩子的声音属敏感数据:不分析性格情绪。
- "一键删除"只承诺**删除本机的录音与派生文件**;**不承诺删除已被玩家导出/分享出去的文件**。
- 含他人声音的作品导出前**提示一次**。

## 14. 音乐生成 LLM/模型:是否值得结合(评估与结论)

### 14.1 评估表(**全部基于已有知识,外部事实 `[待验证]`**)

| 类型 | 代表(待验证)| 放在哪个环节 | 延迟 | 离线 | 普通电脑能跑? | 许可/版权风险 | 成本 |
|---|---|---|---|---|---|---|---|
| **A. 符号生成:LLM 输出结构化音乐数据**(JSON/和弦罗马数字/鼓格/ABC)| 通用 LLM API | **乐队卡、和弦进行建议、鼓型变体、"AI 接话"的动机建议、灯效脚本** | 云端 1~5s(估算);**不能进实时链** | 否(本地小 LLM 在普通电脑上慢且效果差,二期再评)| 云端调用,不占本机 | 与现有曲目雷同的风险较低但需**过滤**;服务商条款 `[待验证]` | 每次几分钱量级(估算)|
| **A'. 符号生成:专用小模型**(Magenta 系 MelodyRNN/Improv RNN/Piano Genie、Music Transformer 类;Apache-2.0 `[待验证]`)| Magenta(项目是否仍活跃 `[待验证]`)| **"AI 乐队成员接话/即兴"**;可本地推理 | 小模型 CPU 上可到交互级 `[待验证]` | **能** | 多数能,但 TensorFlow 依赖重;可转 ONNX `[待验证]` | 代码许可友好;**训练数据版权需核** | 无云成本 |
| **B. 音频生成(本地开源)** | MusicGen(代码 MIT,**权重 CC-BY-NC**)、Stable Audio Open(Stability 社区许可,有收入门槛等条款)`[待验证]` | "把你的循环扩展成完整曲子/氛围底噪" | **秒到分钟级,通常需要 GPU**;**不能实时** | 能(要 GPU 与数 GB 模型)| **普通电脑不行** | **MusicGen 权重非商用 → 不得进商用产品**;Stable Audio Open 条款需核 | 玩家电脑成本;包体巨大 |
| **C. 云端整曲服务**(Suno/Udio 类)| `[待验证,含版权诉讼/授权现状]` | "把你存的歌变成完整带人声的曲子" | 数十秒~分钟 | 否 | 云端 | **商用权/版权纠纷/用户内容上传**风险最高 | 按次计费 |
| **D. 音色/风格迁移**(DDSP、RAVE 类)| Magenta DDSP(Apache-2.0)、RAVE(IRCAM,许可 `[待验证]`)| "用用户录的声音变得更像乐器" | RAVE 可实时但吃资源 `[待验证]` | 能 | 视模型而定 | 涉及人声滥用/肖像风险 | 工程大 |

### 14.2 核心取舍:为什么"符号生成 + 本地即时规则引擎"优于"音频生成"(对小白产品)
1. **可玩性要求结构化数据。** 我们的产品是"格子上的键 + 每个音对应的灯 + 和弦色块 + 可保存的循环层"。**音频生成给的是一段波形——不知道哪个音在哪一拍,灯光无法联动,键位无法映射,玩家改不了任何一个音。** 它能听,但不能"玩",也不能让玩家产生"我创作的"感觉。
2. **"不会错"要求可控。** 符号层可强制和弦/音阶/节拍合规(我们的自动检查);音频生成无法保证与玩家正在按的键同调同拍。
3. **延迟与离线。** 音频生成秒~分钟级、通常需 GPU,普通电脑跑不动;符号规则引擎毫秒级、离线可用。
4. **版权与合规。** 权重非商用的音频模型、云端整曲服务的商用与版权风险最高。
5. **成本。** 符号 + 规则的边际成本近乎为零。

**但要承认音频生成的优势:** 它的**质感和"一键成歌"的震撼**远超我们的内置音源。所以放二期、可选、云端、**玩家主动触发**,作为"把我存的歌升级一下"的彩蛋,而不是核心玩法。

### 14.3 结论

| 档 | 内容 |
|---|---|
| **MVP 用** | **A:LLM 输出受控结构化数据(乐队卡/和弦/鼓型变体/灯效脚本)+ 本地规则引擎实时演奏。** LLM 不进实时链。 |
| **二期评估** | **A':小型本地符号模型**(Magenta 系/ONNX 化)做"接话/即兴动机"——**以 6.2 的 A/B 结果为准**,若规则引擎的"接话"已让玩家满意就不上。<br>**D(音色迁移)**:仅当"重采样音色"不能让玩家满意时评估。<br>**C:云端整曲服务**:仅作为玩家主动点的可选彩蛋,须先解决版权/商用/上传同意。 |
| **不做** | **实时音频生成**(延迟/算力不成立);**非商用权重(如 MusicGen 权重)进商用包**;**默认上传用户录音或作品到任何云端**;**声音克隆类功能**。 |

## 15. Ableton Live 兼容(压缩版:只是"出口",不在任何必经路径)

**结论:MVP 与全部核心体验完全自包含(内置音源 + 内置音乐引擎 + 内置 AI),不依赖 Live,不增加任何用户可见的概念或步骤。**

**事实:**
- 本机**未安装 Live**(0.0,只读检查,实测)。目标用户也没有 Live(用户确认)。
- Mini 用户手册说明随机附 Live Lite 并由 Live Session View 触发 clip [`docs/launchpad-mini-user-guide-v2-en.pdf`——**型号错配,仅作旁证**];Live 对 Launchpad MK2/Mini MK2 是否内置控制脚本 `[待验证]`。
- Live 的 Python Remote Script / Live Object Model / Max for Live / 开源桥(AbletonOSC、ableton-js 等 `[待验证:许可与维护状态未核]`)都是"让 agent 控制 Live"的可能通道,**但都要求用户装 Live,与本产品定位冲突,不做**。
- Live 价格与版本 `[待验证]`,**不作为本方案任何决策依据**。

**我们做什么(低成本出口):**

| 出口 | 内容 | 阶段 |
|---|---|---|
| 导出标准 MIDI(`.mid`)+ 分轨 WAV | 玩家拖进任何 DAW(含 Live)继续做 | **MVP 随"存歌"提供** |
| 导出 Live Set(.als,gzip XML,格式私有且随版本变)| 风险高、收益只对极少数 | **不做**;若要做须先 `[待验证]` 格式 |
| 与 Live 同时运行时的端口冲突 | Live 的控制脚本会独占 Launchpad 端口 | 由 11.2 步骤 3 的"被占用提示"覆盖,**不做联动** |

**灯盘模式冲突:** 我们的软件**独占 Launchpad**,启动时强制 Session 布局(MK2),退出时发全灭并释放端口;不与 Live 共用。
