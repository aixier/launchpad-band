> **修订说明:v2 把 Pad 放在舞台中央是误解,已纠正为"Pad 指挥舞台"。**
> v2 的画面主角是一个 3D 的 Launchpad,乐队和灯光围着它转,舞台成了盘子的背景板。用户的纠正是:**舞台是给 Launchpad 用的**——Launchpad 是指挥棒/控制台,画面的主角是一整个真实感的演出舞台(桁架、摇头灯、雾中的光束、LED 屏墙、地面反射、乐队剪影、观众席),玩家在盘面上的每一次按键、每一次横扫,都是在**指挥这个舞台**,要有"我一个人在指挥一场演唱会灯光秀"的感觉;观感目标是**演奏时的灯光效果要超过专业舞台灯光渲染/预演软件**。
> v3 的改动:① 3D 英雄盘面删除,盘面缩成左下角的小镜像(HUD),引导的青绿 1 Hz 闪烁只在这里表达;② 舞台重做,整页第 3 节重写为"指挥映射 + 灯光导演";③ 渲染从"网格光锥 + 加色面片"升级为自写 GLSL 全屏着色器(第 2.1 节);④ 第 4、5、6 节(灯光语言落实、性能与降级、与专业软件的差异化与评审标准)按新目标重写;⑤ 选型结论(Three.js r149 UMD)沿用。第 1、2、7、9 节保留并按需修订。

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 舞台是什么 | **屏幕是"舞台视角",Launchpad 是指挥台。** 画面 = 一整个舞台:中排桁架 8 盏摇头灯(**= 盘面 8 列**)、后排桁架 4 盏和弦灯、台口 2 盏扫场灯、LED 屏墙、光滑地面、乐队剪影(鼓/贝斯/键盘)、观众席。盘面只在左下角作小镜像(引导期间放大,自由玩收小)。 |
| 怎么"指挥" | 手在盘面上的位置 = 灯的位置:**列 → 哪一盏灯,行 → 光束抬升(1 行压向观众,8 行冲天),音名 → 光色,横扫 → 光浪扫过全场,竖扫 → 光束整体抬起,连击/密度 → 强度(设备无力度),鼓点 → 地面冲击波 + 屏墙环 + 镜头一顿,和弦 → 全场色调转移,能量 → 风格档/镜头推进/烟雾浓度/灯数。**(完整映射表见 3.3。) |
| 灯光师是谁 | **AI 灯光导演**(`director.js`,规则 + 能量曲线,不是机器学习):用户不编灯、不摆灯;导演按音乐能量在"呼吸 / 律动 / 爆发"三档间自动切换,并保证起承转合——有留白、有爬升、触顶时有"落点"(先黑 0.14 秒再炸开)。 |
| 用什么做 | **Three.js r149(UMD)作 WebGL 宿主 + 自写 GLSL**:体积光束、屏墙、地面反射、观众席、辉光、分级都在自写的着色器里。体积光不能靠"网格光锥 + 菲涅耳"做到电影感(第 2.1 节)。Blender 只做后期离线资产,Unreal 不适合(沿用 v2 结论)。 |
| 灯光语言 | 青绿(引导色)**完全不出现在舞台里**:舞台灯色只来自音名色盘(红橙黄紫粉)、和弦色、暖白、金,及其相邻色之间的渐变;引导期间舞台进入**安静模式**(灯全灭,只留低亮度氛围);完成奖励用暖彩虹 + 金,与引导区隔。**4 道自动验证**(静态扫描含 GLSL 字面量、色盘/渐变采样、3600 帧逐帧审计、读渲染像素)。第 4 节。 |
| 性能 [实测] | 本机三种环境、同一份代码、同步基准(不受 vsync 限制)、最重场景 = 爆发档、窗口 1440×860:**独显 Quadro RTX 5000:约 6 ms/帧(最好档,全分辨率)**;**集成显卡 UHD 630:自动档 = "均衡" + 动态分辨率,7~19 ms/帧(多次测量,本机负载不同;在 60 fps 边缘,靠动态分辨率兜底)**,最好档在 UHD 630 上 17~50 ms,所以不会被自动选到;**纯软件渲染(SwiftShader):GLSL 版 300~425 ms/帧不可用,自动换 2D 画布版 8~17 ms/帧**。第 5.1 节。 |
| 视觉目标的诚实说明 | "超过专业软件"是**设计目标,不是已验证的事实**:自评不算数。第 6.3 节给了对照评审标准(并排盲评),需要真人;本文只能证明"哪些维度做得到、哪些维度故意不做"。 |
| 延伸 | 灯光事件流与屏幕解耦,可驱动**家庭灯**(第 7 节,真实硬件本轮不做)。 |

## 1. 要不要虚拟舞台

### 1.1 它解决什么体验问题
对照 `体验设计文档.md`:

| 体验问题 | 现状 | 舞台的作用 |
|---|---|---|
| 光声配合为何"酷":因果感、多感官一致、音乐被看见、**掌控感(体验 7:一人指挥整个场面)** | 只有 80 颗键灯,面积小、不能"铺"出去 | 把"每个音 → 一个对应的光"扩展成整个演出空间:**一个键对应一盏真的灯**,手扫过去光就扫过去。同步第一:手一按,耳朵听到、眼睛看到同一帧。 |
| 观赏性(体验 10) | 桌面镜像盘面只是平面 | 全屏表演 = 投屏即演出,观众看到的是"一场灯光秀",而不是一块小盘子 |
| 作品分享(体验 11) | 规划中,只有音频 | 录制成视频(舞台画面 + 合成器声音 → webm) |
| AI 乐队成员"看得见"(体验 7) | 乐队只是声音 | 鼓手、贝斯手、键盘手在舞台上有剪影、有出场、随节拍动作 |

### 1.2 哪些场景有价值,哪些是炫技
| 场景 | 判断 | 理由 |
|---|---|---|
| 自由玩(已走完引导) | **有价值,效果放开** | "只有高潮才爆发"的前提是有能量曲线 |

| AI 乐队出场 | **有价值** | 开乐队/开鼓点时对应成员"亮起来" |
| 录制分享 | **有价值** | 作品有画面 |
| **新手引导(跟弹、开乐队、开鼓点、换调、练习)** | **必须让位** | P1/P3:灯是唯一的老师。舞台进入**安静模式**:灯全灭,只剩低亮度氛围,按键不唤醒舞台 |
| 没人操作时自动播放的"屏保式"灯效 | **炫技,不做** | 体验文档:"土" = 与音乐无关的循环动画。待机时舞台只是一幅很暗的、缓慢流动的屏墙氛围(亮度 ≈ 自由玩时的 1/4),**束光、粒子全部不亮,镜头只有极慢的漂移** |

## 2. 选型:Three.js vs Blender vs Unreal(及其他)(结论沿用 v2,2.1 为 v3 补充)

约束(来自产品):**小白一键安装、零配置、离线、轻量;普通笔记本集成显卡 60 fps;要与 WebAudio/WebMIDI(或原生音频线程)紧耦合;AI 辅助开发(Claude Code)效率高;可商用且授权清晰。**

| 维度 | **Three.js** | Babylon.js | PlayCanvas | **Blender** | **Unreal Engine** | Unity WebGL |
|---|---|---|---|---|---|---|
| 角色 | 实时渲染库 | 实时渲染引擎 | 实时引擎(云编辑器为主) | 离线 DCC / 渲染器 | 完整游戏引擎 | 游戏引擎 |
| 安装体积 | 库 **约 600 KB**(r149 压缩包 **[实测]** 608 KB);v3 原型(含 three)约 0.77 MB | 数 MB 级 [待验证] | 引擎 ~百 KB~MB 级 [待验证] | 软件本体数百 MB(**不随产品分发**) | 引擎本体数十 GB;打包后的最小可运行程序也是几百 MB 量级 [待验证] | 构建产物数 MB~数十 MB [待验证] |
| 启动时间 | 页面加载即用,**[实测]** 无头里 2.6 s 内可交互(含 SwiftShader) | 同量级 [待验证] | 同量级 [待验证] | 不适用(不在运行时) | 秒级~十秒级 [待验证] | 数秒 [待验证] |

**推荐:Three.js。** 一句话理由:它是唯一同时满足"几百 KB、双击离线、集成显卡 60 fps、与 WebAudio 同时钟、AI 能直接写直接调"的方案,而"电影感"需要的体积光束、雾、辉光、地面反射在 WebGL 上要靠**自写 GLSL** 实现(第 2.1 节;v3 已做)。

**Blender 的合理角色:离线做资产,导出 glTF。** 例如 V1 里更精致的鼓、贝斯、和弦手形象、键帽倒角、烘焙好的环境光/接触阴影纹理;导出 glTF + 压缩纹理后由 Three.js 加载(GLTFLoader 在 r149 是 ES module 示例文件,需要用打包器合成 IIFE,见 `vendor/README.md` 升级路径)。**产品运行时不带 Blender,也不做运行时渲染。**(本次未调用 Blender MCP,因为 MVP 的形体全部用程序化几何,没有必要做离线资产。)

**Unreal 为什么不适合,以及何时才适合:** 与我们所有约束反向——体积以 GB 计、需要独显、与 WebAudio/WebMIDI 无原生联动、AI 难以闭环验证、授权有版税条款 [待验证]。**只在这种条件下才值得:** 把"舞台"变成线下展台/发布会的**高端实体演出**(固定 RTX 级机器、有专人、追求电影级离线渲染),此时可以由 Unreal 接收我们的**灯光事件流**(第 7 节的 schema,经 OSC/Art-Net/WebSocket)做另一个"演出版舞台"——它是事件流的又一个订阅者,不是产品内置组件。

**为什么不选 Babylon/PlayCanvas:** 能力足够,但没有任何一项让它们在我们的约束下明显优于 Three.js;Three.js 的 AI 训练资料与社区示例最多,本项目选最稳的。

**桌面壳(与选型正交,待产品定):** 纯浏览器(开发/演示)· Tauri(体积小,依赖 WebView2;WebMIDI 在 WebView2 里是否可用 [待验证])· Electron(最省心、Chromium 自带 WebMIDI、体积大)。产品方案 v3 提到实时音频建议 C++/Rust 线程:若音频走原生,舞台通过**同一份灯光事件流**(WebSocket/IPC)接收,不依赖 WebAudio——事件流设计正是为此解耦(第 7.1 节)。

### 2.1 新目标带来的技术补充:自写 GLSL 体积光、后处理取舍(v3 新增)

**为什么 v2 的做法到不了"电影感"。** v2 的光束 = 两层圆锥网格 + "法线·视线"菲涅耳衰减 + 加色混合。它做不到:① **雾里的散射**(光束该有烟雾的颗粒起伏、该在近灯口处亮、朝向镜头时炸开,而不是一个均匀发光的塑料锥);② **光束相交处的亮部**(加色混合能叠加,但锥面是"壳",穿进另一束光里的部分没有体积);③ **光束落在墙/地上的光斑与图案(gobo)**,以及它们在地面上的反射;④ 光束被烟雾"吃掉"、与屏墙共同照亮空气。这几项恰恰是专业预演软件里"看起来像真的"的来源,也是我们要超过它们的地方。

**做法(`stage.js` 里的 stage shader,一个全屏片元着色器):** 每个像素发一条射线 →
1. 求与地面(y=0)、屏墙平面(z=-17)的交点,得到该射线的"可见长度";
2. **对每束光:解析求视线与光锥的交段**(二次方程,命中的像素才进入步进)——绝大多数像素对大多数光束是"零成本跳过";
3. 在交段里**步进积分散射**:光锥内的亮度剖面(边缘柔、芯亮)× 相函数(前向散射,光束朝向镜头时极亮)× 烟雾密度(噪声纹理驱动,随时间漂移,越高越稀)× 距离衰减 × 光束内沿轴的条纹;每个像素的步数按交段长度动态(3~12 步),并用交错噪声抖动起点;
4. 墙和地上的**光斑**:对每束光,用同一个锥参数判断表面点是否在锥内,并在锥横截面的局部坐标里叠加 gobo 图案(柔圆 / 破碎光斑 / 五角星 / 线条),光斑随灯的仰角/偏摆移动;
5. **地面反射**:地面点按镜面反射方向取屏墙图案(带轻微噪声扰动);最好档再对反射射线做 3 步的光束积分(地面里能看到光束的倒影);
6. 屏墙是**程序化 LED 图案**(像素间距的点阵遮罩 + 四种图案:缓流极光 / 随频谱的均衡器 / 鼓点冲击环与放射线 / 盘面按键位置的彗星),按风格加权混合;
7. 观众席:屏幕空间的程序化剪影(3 层视差,抬手数量随能量增加),不占网格。

之后:世界网格(桁架、灯体、乐队剪影、火花/彩带粒子,剪影的"逆光边缘"在着色器里由图案的边缘差分得到)→ 灯口光晕/镜头光斑(含变形镜头式的横向拉丝)→ **辉光**(HDR 半浮点渲染目标,第一步直接 4× 降采样,再 4 级金字塔下采样 + 上采样叠加)→ 合成:ACES 色调映射、暗部偏梅红的色彩分级(**不偏青**)、暗角、胶片颗粒、底鼓时的径向"一顿"。

**对 Three.js 选型的影响:** three 只作 WebGL 宿主(渲染器、渲染目标、材质/几何、拾取之外的 API 基本不用)。选型结论(r149 UMD、`file://` 可开、MIT)不变;这些着色器与 three 版本无关,将来换打包器升级 three 时不受影响。

**在集成显卡上的代价 [实测,同一份代码,同步基准,爆发档]:**
- 解析求交 + 动态步数让"无光束"的基线很便宜;光束数 × 步数是主要变量。UHD 630 上,爆发档、1019×609 内部分辨率:无光束约 7~8 ms,10 束光、6 步约 13~16 ms(本机测量有 ±30% 的抖动,因为同机有其他进程)。
- **最好档(全分辨率 + 14 束 × 12 步 + 地面反射的光束倒影 + 3 层观众)在 UHD 630 上 25~50 ms**,所以集成显卡不会被自动选到最好档;**独显 Quadro RTX 5000 上同一档 5 ms**。
- 辉光第一版从 1/2 分辨率开始下采样,在 UHD 630 上单独就要约 7 ms(半浮点渲染目标的带宽);改为第一步直接 4× 降采样后,整帧从约 31 ms 降到约 16 ms(同时调了步数和分辨率,无法单独归因 [待验证:逐项隔离])。
- 动态分辨率(0.55~1.0)是最便宜的旋钮:场景有雾、有辉光,轻微的分辨率下降几乎看不出来;LED 点阵遮罩按像素覆盖面积自动淡出,避免摩尔纹。
- **WebGL2 + EXT_color_buffer_float/half_float** 才有 HDR 辉光;没有时退到 8 位渲染目标(整体压暗 0.4 倍再合成,高光会被截);没有 WebGL 时退到 2D 画布版(第 5.3 节)。
- **WebGPU:没用。** 它能做更省的体积光(froxel 计算着色器),但 `file://` / WebView2 下是否可用 [待验证],且当前解析求交方案已在集成显卡上够用;列为 V2 研究项。

**重型后处理的取舍:** 不用 `EffectComposer`、不用 SSAO/景深/抗锯齿后处理。"景深"用两种便宜的东西代替:观众席剪影的分层虚化(远层更淡更小)和灯口光晕的柔边;抗锯齿靠"雾 + 辉光 + 颗粒"的整体柔化与剪影纹理自带的 alpha 边缘,没有 MSAA(渲染目标里不开)。代价:硬边(桁架细线)在低分辨率档会有锯齿——已在 21 号截图里看到,属已知取舍。

### 3.4 灯光导演 AI 的规则
"AI 灯光导演"是**规则 + 一条能量曲线**,不是学习模型:延迟确定(同一帧)、可测试、不联网、可解释。

1. **输入只有两类**:玩家的按键(位置、时间)和音频时钟里排好的乐队事件(底鼓/踩镲/贝斯/和弦)+ 真实电平与频谱。它不"创作",只"翻译"。
2. **每个光都有来源**(P6:光是音乐的结果,不是装饰)。没有输入时舞台不会自己演:待机 = 很暗的屏墙氛围。
3. **起承转合状态机**:`idle → verse → build → climax → break`。build:能量近 1.5 s 上升 >0.1 且 >0.35;climax:落点后或能量 >0.72;break:离开 climax 4 s 内。导演只用这些状态决定"要不要留白""要不要落点"。
4. **约束优先于效果**:频闪 ≤3 Hz;亮度总和上限;安静模式压倒一切;灯色只能从色盘/渐变里取(`audit()` 每帧可查);减少动效 = 关闭所有"不是回应按键的运动"。
5. **三档风格表**(`STYLES`)是我们的资产:每档定义光束宽度、烟雾、各灯组基础亮度、屏墙图案权重、扇开角度、摆动幅度、镜头推进、辉光强度、是否允许频闪。用户只会在设置里看到"AI 自动 / 呼吸 / 律动 / 爆发"。
6. **后续可替换**:导演的输入/输出是纯数据(`rig`),将来可换成学习模型或 LLM 离线编排,而渲染器不用改;但实时路径坚持规则(延迟与可预测)。[待验证:是否需要离线"整首歌的灯光脚本"——取决于"生成整首歌"的产品形态]

### 3.5 三种舞台风格(AI 自动按能量切换,也可在设置里固定)
| 风格 | 能量 | 光束 | 屏墙 | 灯组 | 镜头 | 其他 |
|---|---|---|---|---|---|---|
| **呼吸** | <0.30 | 宽而柔(tan 0.085),只有后排 4 盏 + 被按的灯 | 缓流极光为主,彗星 | 低亮度,慢摆 | 几乎不推,极慢漂移 | 无频闪,无彩带 |
| **律动** | 0.30~0.62 | 中(0.06),8 盏灯随拍子"追逐"(chase)+ 后排 + 扫场 | 均衡器为主,极光退后 | 阵型每小节换(外开/交叉/摆动) | 推进 30% | 底鼓全体轻脉冲 |
| **爆发** | >0.62 | 窄而亮(0.048,亮度按 1/宽度² 补偿),14 盏全开 | 均衡器 + 冲击环 + 放射线 | 交叉成"星芒"(全部光束汇到墙上一点) | 推进 100% + 落点冲推 | 允许频闪(≤3 Hz);彩带 |

### 3.6 镜头运动(推拉摇移)
- **推/拉**:能量 → 机位前移最多 3.6 m、略降 0.45 m、视野 40°→37°;落点冲推 1.4 m 后回落;留白时缓缓拉回。
- **摇**:注视点 x 方向 ±0.9 m 的慢摆(周期约 2 分钟)+ 跟手偏置(最近按的列 → 注视点轻轻偏向那一侧,3 秒衰减)。
- **移**:机位 x 方向 ±1.3 m 的慢移。**升降**:±0.35 m。
- **一顿**:底鼓时 0.3 m 前冲 + 极小抖动 + 画面径向缩放 1.2%(**不做色散**:红蓝错位会在亮边产生青色,违反色相独占,见第 8 节)。
- 安静模式与"减少动效":静止。表演模式:机位更低更远、更广。

### 3.7 用户侧只有四件事
| 事 | 入口 |
|---|---|
| 弹 | 左下角盘面 / 键盘 / (产品里)真实灯盘 |
| 选舞台风格(或不选) | 菜单 → 设置 → 舞台风格:AI 自动 / 呼吸 / 律动 / 爆发 |
| 全屏表演 | `P` 键或"表演" |
| 录制分享 | "录制"按钮(再点结束,自动下载 webm) |
没有灯具库、灯位编辑、场景编程、时间轴。

### 3.8 视觉叙事(给前端的"美学观点")
舞台是**暗室**:接近纯黑的底,烟雾极淡,**颜色只出现在被指挥过的地方**。界面本身是暖黑 + 暖白的小字,不用渐变卡片、玻璃拟态、紫蓝渐变;顶栏三个动作和一条能量细线,其余全部退到抽屉。**颜色只属于音乐;青绿只属于"下一步"**——整块屏幕上唯一的青绿永远在左下角的盘面镜像和它旁边的提示色块里。

## 4. 如何严格遵守灯光语言(舞台版)

### 4.1 规则 → 舞台落实 → 验证
| 规则 | 舞台里怎么落实 | 自动验证 |
|---|---|---|
| 引导 = 青绿 `GUIDE(0,63,40)` + 1 Hz 硬闪,全局同相 | **只在左下角盘面镜像里**(键色直接来自 `LPCore.tick()`),和它旁边"下一步"提示的色块(同一个 `Core.cue(t)`)。**舞台里没有引导元素**(舞台不教人按哪个键) | `check_lightlang.js` C 段:引导链 5 个阶段 + 练习课,每帧所有引导键同亮同灭,翻转周期 0.5 s;浏览器里每帧运行时检查(设置页"现在检查") |

| 整盘白底 / 柔和模式 / 光敏 | 盘面镜像沿用 v2(白底 26/63;柔和闪烁相位不变);舞台:**闪光 ≤3 次/秒**(0.34 s 最小间隔)、大面积亮度变化慢、"减少动效"关闭频闪 | **F6**(频闪上限)、**F8**(减少动效) |

### 4.2 本次又发现的一条违规(自动审计抓到的)
最初的合成着色器里做了**色散**(底鼓时 R、B 通道反向错位),这在高亮度的边缘会产生**青色边**——违反色相独占。运行时"读像素"审计在爆发档报出 25 个青绿像素(6 帧采样),定位到色散后移除,改为径向缩放"一顿";复测 0 个像素(9 帧采样)。**这类问题静态扫描和灯色审计都抓不到,只有读渲染结果才能抓到**——所以保留这一道。

### 4.3 与 Python 原型的差异(沿用 v2,不变)
Python/v1 的完成彩虹按 HSV 扫完整色环,会扫过青绿色相;v2/v3 的 `pad.js` 用"暖彩虹"(`rainbowHue()`)。**这是唯一的行为差异,建议回灌 `playground.py` 并给 `test_guide_language_is_exclusive` 增加一条"彩虹整段不含引导色相"**(README 决策记录已写"完成彩虹改暖彩虹",`app/` 未动)。

### 4.4 验收办法
1. **自动(每次改动必跑):** `node tools/check_lightlang.js`(A~E 沿用 v2,F1~F9 是 v3 的舞台行为测试;无需浏览器)。
2. **运行时:** 菜单 → 设置 → "灯光语言自检 → 现在检查"(3 秒内审计灯色 + 渲染像素 + 引导同相),或无头脚本 `tools/headless_check.mjs` 的 `audit` 字段。
3. **人工:** 任一时刻,屏幕上带青绿色的元素只能是"下一步该做的事";逐帧录屏复核。
4. **真人:** 静音只看盘面镜像 1 分钟,问"下一步该按哪个"——应当 100% 指对(拟定验收线)。

## 5. 性能预算与降级

### 5.1 预算与实测
目标:普通笔记本**集成显卡** 60 fps(≤16.6 ms/帧);高端独显"开满"。
**测法:** `Stage.bench()`——每帧渲染后 `readPixels` 强制 GPU 完成,得到**不受 vsync 限制**的真实单帧耗时(含 CPU:导演、uniform、粒子、three 提交);36 帧取平均,三种场景(安静 = 新手引导期;律动;爆发 = 最重)× 三档画质。环境:ThinkPad P53(Intel UHD 630 + NVIDIA Quadro RTX 5000)、Chrome 155 无头、`file://`、窗口 1440×860、ANGLE/D3D11。内部分辨率 = 画布像素 × 档位上限 × 动态系数。脚本:`tools/headless_check.mjs`(`--gpu --dgpu` / `--gpu` / 无参数)与 `tools/perf_probe.mjs`;结果 JSON 在 `tools/results/`。

| 环境 | 画质档(内部分辨率) | 安静 | 律动 | 爆发 |
|---|---|---|---|---|
| **独显 Quadro RTX 5000** | 最好(1440×860,14 束 × 12 步 + 光束倒影 + 3 层观众) | 4~6 ms | ~6 ms | ~6 ms |
| | 均衡(960×573) | ~2 ms | ~4 ms | ~4 ms |
| **集成显卡 UHD 630** | 最好(1440×860) | 9~15 ms | 17~33 ms | 17~50 ms |
| | **均衡(960×573,10 束 × 6 步)= 集成显卡默认档** | 5~13 ms | 9~23 ms | **7~19 ms** |
| | 省电(818×489,8 束 × 4 步,无辉光,30 fps 封顶) | 4~12 ms | 6~15 ms | 8~13 ms |
| **纯软件渲染 SwiftShader**(GLSL 版,强制) | 均衡 / 省电 | 408 / 297 ms | 413 / 304 ms | 425 / 300 ms(**不可用**) |
| 软件渲染下的**自动降级 = 2D 画布版** | 1440×860,CPU 绘制 | **~8 ms** | | **~17 ms**(p95 26 ms) |

读法与保留:
- UHD 630 上同一档在不同次测量里差到 2 倍(例如均衡档爆发 7.3 / 15.8 / 16.3 / 18.7 ms),因为同一块 GPU 还在给桌面合成,且本机有其他进程;所以表里写区间而不是单点。**结论是"均衡档大多在 60 fps 边缘",靠动态分辨率兜底,不是"稳 60"。** 没有在更老的集成显卡(HD 4000 等)、4K、多显示器上测过 [待验证]。
- **最好档在 UHD 630 上不可用(17~50 ms)**,所以自动档对 Intel/UHD/Iris/Adreno/Mali 等起步在"均衡";独显上自动档 = 最好,约 6 ms,有 2.5 倍余量(可以以后加更重的效果,例如更多步数、更细的烟雾)。
- 软件渲染下 GLSL 版 300~425 ms/帧(2~3 fps),**所以检测到软件渲染(SwiftShader/llvmpipe/Basic Render)时不进 WebGL 路径,直接用 2D 版**(`?gl=1` 可强制 WebGL,用于测量)。v2 的网格光锥版在软件渲染下是 90 ms/帧——**v3 的写实度是拿软件渲染的可用性换的**,代价明确。
- 绘制调用与资源:WebGL 管线一帧约 33 次绘制(1 个全屏舞台 + 桁架/灯体 14 + 剪影 3 + 粒子 2 + 灯口光晕 1 + 辉光 7 + 合成 1),纹理 10 张(噪声 256²、频谱 16×1、3 张剪影、渲染目标),着色器程序 10 个左右,无外部图片/字体/模型。体积:three 608 KB + 自有代码约 150 KB(`director.js` 23 KB、`stage.js` 约 56 KB、`views.js` 24 KB、`pad.js` 16 KB 等)。
- **录制** [实测]:真实 GPU 下 4 s 约 1.5~2.0 MB(webm,vp9+opus);2D 版 64 KB(分辨率低,内容简单);GLSL 版在软件渲染下取不到帧。

### 5.2 画质档与自适应
| 档 | 内部像素上限 | 光束数 × 步数 | 地面倒影 | 观众层数 | 辉光 | 帧率 |
|---|---|---|---|---|---|---|
| 最好(独显) | 1.6 M | 14 × 12(按交段长度动态 3~12) | 光斑 + 光束倒影 | 3 | 有(HDR) | 60 |
| 均衡(集成显卡起步) | 0.55 M | 10 × 6 | 光斑 + 屏墙倒影 | 2 | 有 | 60 |
| 省电 | 0.4 M | 8 × 4 | 同上 | 1 | 无 | 30 封顶 |
| 平面版(无 GPU) | — | 2D 渐变光束 | 光斑 | 剪影 | 无 | 60 |

- **初始档**:读 `WEBGL_debug_renderer_info`,Intel/UHD/Iris/Adreno/Mali/PowerVR 起步"均衡",软件渲染者直接"平面版",其余"最好"。设置里可固定:自动 / 省电 / 均衡 / 最好。
- **自适应(v3 改进)**:① **动态分辨率先动**(系数 0.55~1.0,每次 −0.12,连续 1.2 s 平均帧时间 >20 ms 才动);② 系数到下限还慢 → 降一档;③ **稳定 6 s 低于 20 ms → 试探性回升 0.06;回升后 4 s 内又变慢 → 回退并锁定 45 s**。针对 v2 记录的"只降不升、偶发卡顿被误降"问题做的改进 [待验证:长时间真人机型上的收敛行为;本轮只做了无头短测]。
- **安静模式**本身就是降载:引导期间灯全灭,体积光步进整个跳过(无命中)。

### 5.3 减少动效 / 低功耗 / 降级
- `prefers-reduced-motion`(系统)或设置里"减少动效":镜头静止(只剩极慢漂移)、**无频闪**(闪光上限 0.25)、无推进/晃动、无粒子(火花、彩带)、光束摆动幅度降到 30%;**灯对按键的回应保留**(它是因果反馈)。**[实测]** 无头里模拟 `reduce`,界面报"reduced=true",测试 F8 通过。
- 页面不可见:`requestAnimationFrame` 自动暂停;音频照常;自适应在隐藏时不评估。
- **无 WebGL / 软件渲染 / 着色器编译失败**:自动换 2D 画布版(同一份导演状态,同一份灯光事件流,录制可用),并用大白话说明;**[实测]** 强制无 WebGL 的路径可玩。
- 没有 WebGL2 的浮点渲染目标:退到 8 位 HDR(压暗 0.4 倍合成)[未实测,代码路径存在]。

### 5.4 风险
- 集成显卡"均衡档"在爆发时可能掉到 50 fps 左右,动态分辨率会让画面略软;**这是已知取舍**。
- three 固定 r149(升级需打包器,见 `vendor/README.md`);自写着色器与 three 版本无关。
- `captureStream` 在纯软件渲染的 GLSL 路径下取不到帧(2D 路径正常)。
- Safari/旧浏览器、WebView2(Tauri)下 WebGL2 与 HDR 渲染目标 [待验证]。

本节对 Capture、WYSIWYG、Depence、MagicVis 等的描述来自通用认知,**未逐项核实** [待验证];本次没有安装或运行它们(约束:不装系统软件)。

### 6.3 对照评审标准(需要真人;自评不算数)
**方法:** 用同一首 30 秒的钢琴/鼓点素材,分别录:① v3 舞台(含手势:横扫、竖扫、连击、落点)的屏幕录像;② 专业预演软件(Capture/WYSIWYG/Depence 任一,由有授权的人)对同一音乐的官方演示/自制片段。两段并排、**随机左右、不标来源**,5~8 位评审(至少 3 位不懂灯光的普通人 + 2 位懂的人)盲评。

| 评审项 | 怎么问 | 通过线 [拟定,待真人校准] |
|---|---|---|
| **因果可归因** | 静音,只看画面:"刚才手是在盘面左边还是右边?按得高还是低?"(给出 10 个短片段) | ≥80% 判对左/右;≥70% 判对高/低 |

## 7. 配套家庭灯光:把虚拟舞台延伸成"家庭舞台"(设计与接口预留,本轮不接硬件)

### 7.1 与屏幕解耦的"灯光事件流"
屏幕舞台不直接驱动灯,而是每帧先**产出一份数据**,屏幕和家庭灯都只是它的订阅者(`Stage.onBus(fn)`,`stage.js: drive()` 里每帧由灯光导演的 `rig` 汇总出来):

```
LightBus {
  t:        number          // 秒,本帧时间(与 performance.now 同源)
  quiet:    boolean         // 是否安静模式(引导期间为 true)
  chord:    "I"|"IV"|"V"|"vi"
  style:    "呼吸"|"律动"|"爆发"
  energy:   0..1
  zones: {                  // 8 位 sRGB;家庭灯按自己的灯区映射
    wash:   [r,g,b],        // 氛围灯:最近一个音的颜色,随时间衰减
    strip:  [r,g,b],        // 灯带:和弦色 × 电平(安静模式下 = 引导色)
    accent: [r,g,b]         // 点缀/鼓点灯:鼓点橙,随底鼓闪一下
  }
  events: [ {kind:"kick"|"hat"|"bass"|"pad", midi?} ]   // 本帧新触发的节拍/和弦事件
}
```
**要点:** ① 一份数据,两种用途——屏幕里的 3D 灯与家庭灯**读同一份**,不会各做一套、更不会两套灯光语言;② 灯区(zones)是抽象的 3 个,与具体灯珠数无关,真实灯具在**接收端**映射;③ 不依赖 Three.js:产品里音频走原生时,事件流由原生侧产出,屏幕舞台与家庭灯都订阅它;④ 事件携带音频时钟时间戳,可**提前发送**(7.3)。后期的 Art-Net/sACN 输出器只是另一个订阅者。

### 7.2 灯光语言在家庭灯上的落地
| 阶段 | 家庭灯行为 | 理由 |
|---|---|---|
| **引导期间(`quiet`)** | **默认只有"灯带"一区**跟随全局引导相位,颜色为同一青绿、同一 1 Hz 同相(`Core.cue`);其余灯区转暗暖色(`34,28,22`),不跳动 | 引导语言唯一;家里的灯不能与盘面抢"该按哪"。更保守的选项:引导期间家庭灯完全不亮(设置里可选) |
| 自由玩/表演 | 放开:氛围灯随音名色,灯带随和弦色与电平,点缀灯随底鼓 | 灯光是音乐的结果 |
| 完成仪式 | 暖彩虹扫过 + 金色点缀 | 奖励与引导区隔 |
| 色相独占 | 事件流里除"安静模式下的引导色"外,**任何灯区不得出现青绿色相**;审计函数已覆盖事件流(`Stage.audit()`) | 与屏幕同一规则 |
| 光敏安全 | 亮度变化不超过 3 次/秒的闪烁;**禁止频闪**;设置里有亮度上限与"夜间静音时段"(V1) | 家居场景(卧室、孩子) |

### 7.3 延迟预算:按键 → 声 → 屏幕 → 家庭灯
- 参照 ITU-R BT.1359-1 对音画同步的结论:**声音早于画面**约 **45 ms** 开始可察觉,约 **90 ms** 起不可接受(画面领先声音的容限更大,约 125/185 ms)[待验证:数值以标准原文为准;此为电视/视频场景,**打击乐/钢琴类乐器的敏感度更高** — 体验文档里"20 ms 同步阈值"为经验说法,同样待验证]。
- 链路预算(目标**家庭灯相对声音的滞后 ≤ 50 ms,硬上限 90 ms**):

| 段 | 估计 | 依据 |
|---|---|---|
| 灯盘 USB → 主机 | 1~几 ms | 低速 USB MIDI;README 指出本机"按键到电脑"未测 [待验证] |
| 主机 → 声音进混音 | ~7 ms,到耳约 20~30 ms | README 实测/估计 |
| 屏幕 | ≤ 1 帧(16.7 ms) | **[实测]** 60 fps |
| **ESP-NOW**(主机侧 USB 网关板 → 广播 → 灯节点) | 空口约几 ms + 串口/调度 | 乐鑫文档称延迟低、无需握手 [待验证数值];本项目已有台架报告可参考(`c3_control/docs`:ESP-NOW 实测丢包 6~7%,有 ≥1 s 断流)——**家庭灯用场景对丢包容忍高(下一帧补上),但不能依赖单包到达** |
| **Wi-Fi UDP → WLED**(DDP/Art-Net/sACN) | 典型 5~20 ms,偶发抖动达数十~上百 ms(路由器省电、拥塞)[待验证] | 取决于路由器与信道占用 |
- **关键技巧(不是预测按键,而是预知节拍):** 鼓/贝斯/和弦是合成器在**音频时钟里提前 120 ms 排好**的,事件流带有目标时刻 T;发送端可以把"T 时刻亮"**提前**发给灯节点,节点用自己的本地计时器在 T 点执行——乐队部分的无线延迟可被完全抵消(前提:发送→到达 < 前瞻窗口,并校时 [待验证])。**只有"用户即时按键"这类不可预知事件**才吃满链路延迟,所以那一类用最低延迟的链路(ESP-NOW 广播)。

**ESP-NOW 广播 vs Wi-Fi UDP(WLED)取舍:**
| | ESP-NOW(自定义节点) | WLED + DDP/Art-Net/sACN |
|---|---|---|
| 延迟/抖动 | 低、稳定 [待验证数值] | 依赖路由器,抖动大 |
| 可靠性 | 广播无确认;需要序号+最新状态覆盖 | UDP 也无确认;WLED 本身成熟 |
| 小白安装 | **难**:需要刷自定义固件、网关板、配对 | **较易**:WLED 网页刷机、App 配置、成品 LED 控制器可买 [待验证] |
| 信道 | 与 Wi-Fi 同一信道,**会与其他 ESP-NOW 设备冲突** | 走路由器,不占额外信道 |
| 生态 | 自己维护 | WLED 社区 + QLC+/OLA 都懂 DDP/Art-Net/sACN |
| 建议 | **进阶/极低延迟选项**(V2) | **V2 首选(小白友好)**;乐队部分靠"提前发 + 本地计时"补延迟 |

### 7.4 原型层面(v2 已做,v3 保留)
菜单 → 设置里的"**家庭灯光(占位,未连接任何硬件)**":3 盏模拟灯(氛围灯、灯带、鼓点灯),由 `Stage.onBus` **同一数据流**驱动;一个"**模拟链路延迟**"滑块(0~250 ms)把事件流延后回放——用户(和设计者)可以亲眼看到多少毫秒开始"灯慢半拍",作为延迟预算的直观依据。**[实测]** v2 的无头脚本在设置页读到三盏灯的颜色随按键变化;引导期间仅灯带随引导相位;v3 的 `bus.events` 目前是空数组(预留,舞台内部用 `rig` 直接驱动)。

### 7.5 风险
- **安全**:**只使用低压 LED 灯带(5/12/24 V DC)+ 带认证的电源适配器**;不控制市电、不接继电器开关家电;控制器限制总电流并给出安装说明;任何接线说明必须由有资质的人复核 [待验证:产品化前需合规评估]。
- **信道冲突**:本项目的无人机 ESP-NOW 链路(`c3_control/docs/espnow-link-protocol.md`)固定在同一信道:并行 Wi-Fi UDP 时随路由器(现为 1),ESP-NOW 专用固件默认 **9**(`ch N` 可改),2026-10-21 勘察结果为 1 信道 6 个 AP、11 信道 5 个、8~10 无 AP。**家庭灯不得占用 1 与 9 及其相邻(约 ±2),也不得改动那些板子**;候选(如 13 或 4~5)须现场扫描后定 [待验证],并在设置里可改。家庭灯节点用**独立的 USB 网关板**,不复用无人机的网关(COM16)。
- **成本与难度**:ESP-NOW 方案需要网关板 + 每盏灯一个 ESP32 节点 + 灯带 + 电源 [待验证:零部件价格];小白不会刷固件 → 若产品化应选 WLED 或预刷成品。
- **干扰**:2.4 GHz 拥挤时延迟与丢包上升;家庭灯与音乐无关的断流必须**静默降级**(舞台继续,不弹错误)。
- **体验**:深夜/邻里:亮度上限、夜间静音时段、一键全关。

**看图发现并修掉的问题(本次,按发现顺序)**:
1. **爆发档整屏发白、像糊了一层粉雾**:朝向镜头的宽光束 + 环境雾色 + 屏墙叠加 + 辉光全部过亮。→ 光束窄化(tan 0.12→0.048)并让亮度按 1/宽度² 补偿;环境雾色降到 0.14;辉光阈值 1.1、强度 0.42;屏墙加软限幅。
2. **光束根本看不见**(只有灯口光晕):积分增益偏低,实测要 ×4.5 才出现清晰光柱。→ 增益 4.0,并做成可调 uniform。
3. **光束全朝镜头,没有"光柱"形状**:仰角只在"朝观众"一个方向上变化。→ 改为三个关键方向插值(迎面 / 斜扎台面 / 冲天),交叉阵型把左右偏摆加大,从侧面看才有长光柱和"星芒"汇聚。
4. **辉光太贵**:第一版从 1/2 分辨率开始,UHD 630 上单项约 7 ms。→ 第一步直接 4× 降采样。
5. **读渲染像素的审计在爆发档抓到 25 个青绿像素**:底鼓时的色散(红蓝错位)在亮边产生青色。→ 删除色散,改径向缩放;复测 0。(4.2 节)
6. **观众席像"棒棒糖贴纸"**:手臂又长又粗、手是大圆、全身一圈霓虹描边。→ 手臂短而细、手小、去掉观众描边;乐队剪影的描边改为只在顶部(逆光),侧边减弱。
7. **屏墙下沿悬空、地面看不到倒影**:屏墙底边在 2.2 m,物理上地面只能映出它的下半部。→ 屏墙落到 0.5 m,台面能映出屏墙(`10-afterglow-break.png` 可见)。
8. **gobo 的螺旋图案像棒棒糖/糖果**:→ 换成破碎光斑(噪声阈值)。
9. **待机时屏墙像屏保**:自由玩后 6 s 无输入,屏墙仍有 1/2 亮度的缓流极光。→ 待机亮度降到约 1/4(0.14+0.86×0.1)。
10. **抽屉盖住舞台右侧,还把顶栏三个按钮盖住了**(菜单关不掉)。→ 抽屉打开时舞台与顶栏让出右侧(宽度 410 px),**镜头按宽高比自动后撤**让整个舞台仍在画面里;抽屉里加"×"。
11. **软件渲染下 GLSL 版 300~425 ms/帧**。→ 检测到软件渲染自动换 2D 版(~8~17 ms),并重画了 2D 版(光晕、光束渐变、屏墙均衡器、地面光斑、剪影、观众)。
12. **乐队成员被左下角盘面遮住**:贝斯手/键盘手内移 1.7 m / 1 m。
13. **灯体(黑色圆筒)太大、像随机黑块**:缩小 25%。
14. **F5 测试曾误报"停留不足"**:测试把"开场后第一次换档"当成了"停留不足 3 s",其实距上次换档已 6 s。**是测试写法问题,不是产品问题**,已改为对照 `styleAt`。
